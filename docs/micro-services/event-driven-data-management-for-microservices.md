#Управление данными на основе событий для микросервисов

## 1.1 Микросервисы и проблемы управления распределенными данными

Монолитные приложения обычно имеют реляционную базу данных. Преимущество заключается в том, что приложение может использовать транзакции ACID, что может обеспечить некоторые важные эксплуатационные функции:

1. Атомарность – любое изменение является атомарным.
2. Согласованность. Состояние базы данных всегда согласовано.
3. Изоляция. Даже если транзакции выполняются одновременно, они кажутся последовательными.
4. Долговечность. После фиксации транзакции ее невозможно отменить.

Учитывая вышеперечисленные характеристики, приложение можно упростить: запустить транзакцию, изменить (вставить, удалить, обновить) множество строк, а затем зафиксировать эти транзакции.

Еще одним преимуществом использования реляционной базы данных является то, что она обеспечивает поддержку SQL (мощного декларативного языка запросов с преобразованием таблиц). Пользователи могут легко объединять данные из нескольких таблиц с помощью запросов. Планировщик запросов РСУБД определяет наилучшую реализацию. Пользователям не нужно беспокоиться о базовых проблемах, таких как доступ к базе данных. Кроме того, поскольку все данные приложения находятся в базе данных, их легко запрашивать.

Однако в архитектуре микросервисов доступ к данным становится очень сложным, поскольку данные являются конфиденциальными для микросервисов, и единственный способ получить к ним доступ — через API. Такой способ упаковки доступа к данным делает микросервисы слабосвязанными и независимыми друг от друга. Если несколько служб получают доступ к одним и тем же данным, схема обновляет время доступа и координаты между всеми службами.

Более того, разные микросервисы часто используют разные базы данных. Приложения генерируют множество различных данных, и реляционные базы данных не обязательно являются лучшим выбором. В некоторых сценариях база данных NoSQL может предоставить более удобную модель данных и обеспечить лучшую производительность и масштабируемость. Например, приложение, генерирующее и запрашивающее строки, использует систему поиска символов, такую ​​как Elasticsearch. Аналогично, приложение, генерирующее данные социальных изображений, может использовать базу данных изображений, например Neo4j; поэтому приложения, основанные на микросервисах, обычно используют базу данных, сочетающую в себе SQL и NoSQL, что представляет собой метод, называемый многоязычным постоянством.

Секционированные, многоязычные постоянные архитектуры для хранения данных имеют множество преимуществ, включая слабосвязанные сервисы, а также лучшую производительность и масштабируемость. Однако далее следует проблема управления распределенными данными.

Первая проблема заключается в том, как завершить транзакцию, сохраняя при этом согласованность данных между несколькими службами. Причина этой проблемы в том, что в качестве примера мы берем интернет-магазин B2B. Обслуживание клиентов включает в себя различную информацию о клиентах, например кредитные линии. Служба заказов управляет заказами и должна проверять, не противоречит ли новый заказ кредитному лимиту клиента. В монолитном приложении службе заказов достаточно использовать транзакции ACID только для проверки доступного кредита и создания заказов.

Напротив, в архитектуре микросервисов таблицы заказов и клиентов являются частными таблицами соответствующих сервисов, как показано на следующем рисунке:

![service table](./images/Private-table-of-the-corresponding-service.png)

Служба заказов не может получить доступ к таблице клиентов напрямую, доступ к ней возможен только через API, опубликованный службой поддержки клиентов. Служба заказов также может использовать распределенные транзакции, также известные как двухфазная фиксация (2PC). Однако в текущих приложениях 2PC не является обязательным. Согласно теории CAP, необходимо сделать выбор между доступностью и согласованностью ACID, причем доступность обычно является лучшим выбором. Однако многие современные технологии, например многие базы данных NoSQL, не поддерживают 2PC. Поддержание согласованности данных между сервисом и базой данных является очень фундаментальным требованием, поэтому нам нужно найти другие решения.

Вторая проблема — как выполнить поиск данных из нескольких сервисов. Например, представьте, что приложению нужно отобразить покупателя и его заказ. Если служба заказов предоставляет API для приема информации о заказах пользователя, пользователь может использовать операции соединения, подобные приложениям, для получения данных. Приложение принимает информацию о пользователе от сервиса пользователя и принимает заказ этого пользователя от сервиса заказов. Предположим, что служба заказов поддерживает запрос заказов только по закрытому ключу (возможно, с использованием базы данных NoSQL, которая поддерживает прием только на основе первичного ключа). В настоящее время не существует подходящего метода получения необходимых данных.

## 1.2 Архитектура, управляемая событиями

Для многих приложений решением является использование архитектуры, управляемой событиями. В этой архитектуре микросервисы публикуют событие, когда происходит что-то важное, например обновление бизнес-объекта. Когда микрослужбы, подписывающиеся на эти события, получают это событие, они могут обновить свои собственные бизнес-объекты, а также могут инициировать публикацию дополнительных событий.

События можно использовать для включения бизнес-транзакций в нескольких службах. Транзакция обычно состоит из серии шагов, каждый из которых состоит из микросервиса, который обновляет бизнес-объект и публикует событие, которое активирует следующий шаг. На следующем рисунке показано, как использовать событийно-ориентированный подход для проверки доступности кредита при создании заказа. Микросервисы обмениваются событиями через брокер сообщений.

1. Сервис заказов создает заказ со статусом НОВЫЙ и публикует событие «Событие создания заказа».

![Order-Created-Event](./images/Order-Created-Event.png)

2. Служба поддержки клиентов использует событие создания заказа, резервирует кредит для этого заказа и публикует событие «Событие резервирования кредита».

![Credit-Reserved-Event](./images/Credit-Reserved-Event.png)

3. Служба заказов использует событие «Кредит зарезервирован» и меняет статус заказа на «ОТКРЫТ».

![Status-is-OPEN](./images/Status-is-OPEN.png)

В более сложных сценариях может потребоваться больше шагов, например резервирование инвентаря при проверке кредита пользователя.

Учтите, что (а) каждая служба обновляет базу данных и публикует события атомарно, а затем (б) брокер сообщений гарантирует, что события доставляются хотя бы один раз, прежде чем бизнес-транзакция может быть завершена между несколькими службами (эта транзакция не является транзакцией ACID). Этот режим обеспечивает слабый детерминизм, например, конечную согласованность. Этот тип транзакции называется БАЗОВОЙ моделью.

Вы также можете использовать события для поддержки представлений реализации различных микросервисов с предварительным объединением данных. Служба, поддерживающая это представление, подписывается на соответствующие события и обновляет представление. Например, служба обновления представления заказов клиентов (которая поддерживает представление заказов клиентов) подписывается на события, публикуемые службой поддержки клиентов и службой заказов.

![pre-join](./images/pre-join.png)

Когда служба обновления представления заказов клиентов получает события о клиентах или заказах, она обновляет набор данных представления заказов клиентов. Представление заказов клиентов можно реализовать с использованием базы данных документов, такой как MongoDB, в которой для каждого пользователя хранится один документ. Служба запросов по просмотру заказов клиентов отвечает за ответы на запросы клиентов и недавних заказов путем запроса набора данных просмотра заказов клиентов.

Событийно-ориентированная архитектура также имеет как преимущества, так и недостатки. Эта архитектура может позволить транзакциям охватывать несколько сервисов и обеспечивать конечную согласованность, а также позволяет приложению сохранять окончательное представление. Недостаток заключается в том, что модель программирования более сложна, чем модель транзакций ACID: для восстановления после сбоев на уровне приложения необходимо выполнить компенсационные транзакции, например, если проверка кредитоспособности не удалась, заказ необходимо отменить; кроме того, приложению приходится иметь дело с противоречивыми данными. Это связано с тем, что изменения, вызванные временными (текущими) транзакциями, видны, а проблемы несогласованности данных также могут возникнуть, когда приложение читает окончательное представление, которое не было обновлено. Еще одним недостатком является то, что подписчикам приходится обнаруживать и игнорировать избыточные события.

## 1.3 Атомарные операции Достижение атомарности

Архитектура, управляемая событиями, также сталкивается с проблемой атомарности событий обновления и публикации базы данных. Например, служба заказов должна вставить строку в таблицу ORDER, а затем опубликовать событие Order Created; обе операции должны быть атомарными. Если после обновления базы данных происходит сбой (вылет) службы, в результате чего события не могут быть опубликованы, система становится несогласованной. Стандартный способ обеспечения атомарных операций — использовать распределенную транзакцию, включающую базу данных и брокер сообщений. Однако, исходя из описанной выше теории CAP, это не то, чего мы хотим.

### 1.3.1 Использование локальных транзакций для публикации событий

Один из способов достижения атомарности — использовать многоэтапный процесс, включающий только локальные транзакции для публикации приложений событий. Хитрость заключается в таблице EVENT, которая действует как список сообщений в базе данных, в которой хранятся бизнес-объекты. Приложение инициирует (локальную) транзакцию базы данных, обновляет состояние бизнес-объекта, вставляет событие в таблицу EVENT, а затем отправляет транзакцию. Другой независимый процесс или поток приложения запрашивает таблицу EVENT, публикует событие в брокере сообщений, а затем использует локальную транзакцию, чтобы пометить событие как опубликованное, как показано на следующем рисунке:

![multi-step process](./images/multi-step-process.png)

Служба заказов вставляет строку в таблицу ORDER, а затем вставляет событие Order Created в таблицу EVENT. Поток или процесс публикации событий запрашивает таблицу EVENT, запрашивает неопубликованные события, публикует их, а затем обновляет таблицу EVENT, чтобы пометить событие как опубликованное.

Этот метод также имеет преимущества и недостатки. Преимущество заключается в том, что публикация событий не зависит от 2PC, и приложение публикует события бизнес-уровня, не делая вывод о том, что с ними произошло; недостатком является то, что этот метод может привести к ошибкам, поскольку разработчики должны учитывать события публикации. Кроме того, этот метод представляет собой проблему для некоторых приложений, использующих базы данных NoSQL, поскольку сам NoSQL имеет ограниченные возможности транзакций и запросов.

Этот метод не требует 2PC, поскольку приложение использует локальные транзакции для обновления состояния и публикации событий. Теперь давайте рассмотрим другой способ получить атомарность, просто обновив состояние приложения.

### 1.3.2 Журналы транзакций базы данных майнинга

Другой способ добиться атомарности событий, публикуемых потоками или процессами без 2PC, — это анализ транзакций базы данных или журналов фиксации. Приложение обновляет базу данных и вносит изменения в журнал транзакций базы данных. Процесс или поток анализа журнала транзакций считывает эти журналы транзакций и публикует их брокеру сообщений. Как видно на рисунке ниже:

![No-2PC-required](./images/No-2PC-required.png)

Примером такого подхода является проект LinkedIn Databus. Databus анализирует журналы транзакций Oracle и публикует события на основе изменений. LinkedIn использует Databus для обеспечения согласованности записей в системе.

Другой пример: механизм потоков AWS в AWS DynamoDB представляет собой управляемую базу данных NoSQL. Поток DynamoDB основан на изменениях временных рядов (операции создания, обновления и удаления) в таблице базы данных за последние 24 часа. Приложение может прочитать эти изменения из потока, а затем опубликовать эти изменения как события.

Анализ журнала транзакций также имеет свои преимущества и недостатки. Преимущество заключается в том, что каждое событие выпуска обновления не зависит от 2PC. Анализ журнала транзакций можно упростить, разделив события публикации и бизнес-логику приложения; основным недостатком является то, что журналы транзакций имеют разные форматы для разных баз данных и даже для разных версий баз данных; и трудно преобразовать записи обновления журнала транзакций низкого уровня в бизнес-события высокого уровня.

Метод анализа журнала транзакций напрямую обновляет базу данных через приложение без необходимости вмешательства двух компьютеров. Давайте рассмотрим совершенно другой подход: тот, который полагается только на события без обновления.

### 1.3.3 Использование источников событий

Источники событий обеспечивают согласованность бизнес-объектов за счет использования принципиально другого подхода к центру событий для достижения атомарности, не требующего 2PC. Приложения такого типа сохраняют серию событий изменения состояния бизнес-объектов вместо сохранения текущего состояния объекта. Приложения могут воспроизводить события для восстановления текущего состояния объекта. Всякий раз, когда бизнес-объект меняется, на временную шкалу добавляются новые события. Поскольку событие сохранения представляет собой одну операцию, оно должно быть атомарным.

Чтобы понять, как работает источник событий, рассмотрим в качестве примера сущность события. Традиционно каждый заказ сопоставляется со строкой в ​​таблице ORDER, например в таблице ORDER_LINE_ITEM. А вот для метода источника событий сервис заказов хранит заказ в виде изменения статуса события: создан, утвержден, отправлен, отменен; каждое событие включает в себя достаточно данных для восстановления статуса заказа.

![Event-sourcing](./images/Event-sourcing.png)

События хранятся в базе данных событий в течение длительного времени, а для добавления и получения событий сущностей предоставляются API. Хранилище событий аналогично описанному ранее брокеру сообщений, предоставляющему API для подписки на события. Хранилище событий доставляет события всем заинтересованным подписчикам и является основой архитектуры микросервисов, управляемой событиями.

Метод источника событий имеет множество преимуществ: он решает ключевые проблемы архитектуры, управляемой событиями, позволяет надежно публиковать события при наличии изменений состояния, а также решает проблему согласованности данных в архитектуре микросервисов. Кроме того, поскольку это постоянное событие, а не объект, можно избежать проблемы несоответствия реляционного импеданса объекта.

Метод источника данных обеспечивает 100% надежные журналы мониторинга изменений бизнес-объекта, что позволяет получить статус объекта в любой момент времени. Кроме того, подход к источнику событий позволяет бизнес-логике состоять из слабосвязанных бизнес-объектов, которыми обмениваются события. Эти преимущества позволяют относительно легко перенести одно приложение на архитектуру микросервисов.

Метод источника событий также имеет множество недостатков. Поскольку он использует другие или незнакомые шаблоны преобразования, его нелегко переучить; хранилище событий поддерживает только бизнес-объекты запроса первичного ключа, а для выполнения бизнес-запроса необходимо использовать разделение ответственности за запрос (CQRS). Следовательно, приложение должно обрабатывать в конечном итоге согласованные данные.

## 1.4 Резюме

В архитектуре микросервисов каждый микросервис имеет свой собственный набор данных. Разные микросервисы могут использовать разные базы данных SQL или NoSQL. Хотя архитектура базы данных имеет большие преимущества, она также сталкивается с проблемами в распределенном управлении данными. Первая проблема заключается в том, как обеспечить согласованность бизнес-транзакций между несколькими службами; Вторая проблема заключается в том, как получить согласованные данные из мультисервисной среды.

Лучшее решение — принять архитектуру, управляемую событиями. Одна из возникших проблем заключается в том, как обновлять статус и публиковать события атомарно. Существует несколько способов решения этой проблемы, включая обработку базы данных как очереди сообщений, анализ журнала транзакций и источник событий.
