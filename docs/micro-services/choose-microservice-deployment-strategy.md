#Выбор стратегии развертывания микросервисов

## Предисловие

Развертывание монолитного приложения означает запуск нескольких копий большого приложения, обычно с предоставлением нескольких (N) серверов (физических или виртуальных), на которых выполняется несколько (M) экземпляров приложения. Развертывание монолитного приложения будет непростой задачей, но оно, безусловно, проще, чем развертывание приложения микросервисов.

Приложение микросервисов состоит из сотен сервисов, причем сервисы могут быть написаны отдельно на разных языках и фреймворках. Каждая служба представляет собой отдельное приложение, которое может иметь свои собственные потребности в развертывании, ресурсах, масштабировании и мониторинге. Например, в зависимости от требований службы можно запустить несколько экземпляров службы, но, кроме того, каждый экземпляр должен иметь собственный процессор, память и ресурсы ввода-вывода. Несмотря на сложность, дальнейшая задача заключается в том, что развертывание услуг должно быть быстрым, надежным и экономически эффективным.

Существует несколько шаблонов развертывания микросервисов. Давайте сначала обсудим схему использования нескольких экземпляров службы на одном хосте.

## Режим нескольких экземпляров службы на одном хосте

Одним из способов развертывания микросервисов является режим нескольких экземпляров службы с одним хостом. Используя этот режим, вам необходимо предоставить несколько физических или виртуальных машин и запустить несколько экземпляров службы на каждой машине. Во многих случаях это традиционный метод развертывания приложений. Каждый экземпляр службы работает на одном или нескольких известных портах хостов, которые можно рассматривать как домашних животных.

На следующем рисунке показана эта архитектура:

![deployment-strategy-1](./images/deployment-strategy-1.png)

Этот режим имеет несколько параметров, один из которых показывает, из скольких процессов состоит каждый экземпляр службы. Например, вам необходимо развернуть экземпляр службы Java как веб-приложение на сервере Apache Tomcat. Экземпляр службы Node.js может состоять из родительского процесса и нескольких дочерних процессов.

Другой параметр определяет, сколько экземпляров службы запущено в одной группе процессов. Например, вы можете запускать несколько веб-приложений Java на одном сервере Apache Tomcat или запускать несколько экземпляров пакета OSGI в одном контейнере OSGI.

Модель экземпляра с одним хостом и несколькими сервисами также имеет преимущества и недостатки. Основное преимущество заключается в эффективности использования ресурсов. Несколько экземпляров службы совместно используют сервер и операционную систему. Будет более эффективно, если группа процессов запустит несколько экземпляров службы. Например, несколько веб-приложений используют один и тот же сервер Apache Tomcat и JVM.

Еще одним преимуществом является то, что развертывание экземпляров службы происходит быстро. Просто скопируйте сервис на хост и запустите его. Если сервис написан на Java, вам нужно только скопировать файл JAR или WAR. Для других языков, таких как Node.js или Ruby, вам необходимо скопировать исходный код. Это означает, что нагрузка на сеть очень низкая.

Запуск службы происходит быстро, поскольку нагрузка невелика. Если служба представляет собой автономный процесс, ее нужно только запустить; в противном случае, если это экземпляр службы, работающий в группе процессов контейнера, его необходимо динамически развернуть в контейнере или перезапустить контейнер.

Помимо вышеперечисленных преимуществ, экземпляры нескольких служб с одним хостом также имеют недостатки. Одним из основных недостатков является отсутствие изоляции между экземплярами службы, если только каждый экземпляр службы не является независимым процессом. Если вы хотите точно отслеживать использование ресурсов каждого экземпляра службы, вы не можете ограничить использование ресурсов каждым экземпляром. Таким образом, плохой экземпляр службы может занять всю память или процессор хоста.

Несколько экземпляров службы в одном процессе не изолированы. Например, все экземпляры могут использовать одну и ту же кучу JVM. Плохой экземпляр службы может легко атаковать другие службы в том же процессе; более того, может оказаться невозможным отслеживать ресурсы, используемые каждым экземпляром службы.

Другая серьезная проблема заключается в том, что оперативная группа должна знать подробные этапы развертывания. Сервисы могут быть написаны на разных языках и в разных фреймворках, поэтому команде разработчиков должно быть много возможностей для общения с командой эксплуатации и обслуживания. Сложность увеличивает вероятность ошибок при развертывании.

Как видите, хотя и знакомые экземпляры службы с одним хостом и несколькими службами имеют множество серьезных недостатков. Давайте посмотрим, есть ли другие способы развертывания микросервисов, позволяющие избежать этих проблем.

## Режим одного экземпляра службы с одним хостом

Другой способ развертывания микросервисов — это режим одного экземпляра с одним хостом. При использовании этой модели каждый экземпляр службы на узле независим. Существует два различных режима реализации: один экземпляр одной виртуальной машины и один экземпляр одного контейнера.

### Режим одной виртуальной машины с одним экземпляром

Но в режиме одиночного экземпляра одной виртуальной машины служба обычно упаковывается в образ виртуальной машины (образ), например Amazon EC2 AMI. Каждый экземпляр службы — это виртуальная машина (например, экземпляр EC2), запущенная с использованием этого образа. Следующая диаграмма иллюстрирует эту архитектуру:

![deployment-strategy-2](./images/deployment-strategy-2.png)

Netflix использует эту архитектуру для развертывания службы потокового видео. Netfix использует Aminator для упаковки каждой службы в EC2 AMI. Каждый запущенный экземпляр службы является экземпляром EC2.

Существует множество инструментов, которые можно использовать для создания собственных виртуальных машин. Вы можете настроить службу непрерывной интеграции (CI) (например, Jenkins), чтобы запретить Aminator упаковывать службу в EC2 AMI. Packer.io — еще один вариант автоматического создания образа виртуальной машины. В отличие от Aminator, он поддерживает ряд технологий виртуализации, таких как EC2, DigitalOcean, VirtualBox и VMware.​

Boxfuse использует инновационный подход к созданию образов виртуальных машин, который устраняет следующие недостатки. Boxfuse упаковывает приложения Java в минимальные образы виртуальных машин. Они создаются быстро, быстро запускаются и более безопасны, поскольку имеют меньше сервисных интерфейсов, доступных внешнему миру.

У CloudNative Inc. есть SaaS-приложение Bakery для создания AMI EC2. После того как архитектура микросервисов пользователя пройдет проверку, вы сможете настроить собственный CI-сервер для активации Bakery. Пекарня объединяет услуги в AMI. Использование приложения SaaS, такого как Bakery, означает, что пользователям не нужно тратить время на настройку собственной архитектуры создания AMI.

Модель экземпляра службы для каждой виртуальной машины имеет множество преимуществ. Основное преимущество виртуальной машины заключается в том, что каждый экземпляр службы работает полностью независимо, со своим собственным независимым процессором и памятью и не занят другими службами.

Еще одним преимуществом является то, что пользователи могут использовать зрелые облачные архитектуры, например, предоставляемые AWS, а облачные сервисы предоставляют полезные функции, такие как балансировка нагрузки и масштабируемость.

Еще одним преимуществом является то, что технология реализации услуг является автономной. Как только служба упаковывается в виртуальную машину, она становится черным ящиком. API управления виртуальной машиной становится API службы развертывания, а развертывание становится очень простой и надежной вещью.

Модель с одной виртуальной машиной и одним экземпляром также имеет недостатки. Одним из недостатков является то, что использование ресурсов неэффективно. Каждый экземпляр службы занимает ресурсы всей виртуальной машины, включая операционную систему. Более того, в типичной общедоступной среде IaaS ресурсы виртуальных машин стандартизированы и могут не использоваться полностью.

Более того, общедоступная IaaS взимается в зависимости от виртуальной машины, независимо от того, занята ли виртуальная машина; например, AWS предоставляет возможности автоматического расширения, но не обеспечивает быстрого реагирования на приложения по требованию, что вынуждает пользователей развертывать больше виртуальных машин, что увеличивает затраты на развертывание.

Еще одним недостатком является то, что развертывание новых версий сервисов происходит медленно. Образы виртуальных машин создаются медленнее из-за их размера. По этой же причине инициализация виртуальной машины также происходит медленнее, а запуск операционной системы также требует времени. Но это не всегда так, некоторые легкие виртуальные машины, например созданные с помощью Boxfuse, работают быстрее.

Третий недостаток заключается в том, что операционная группа отвечает за множество настроек. Если только вы не используете такой инструмент, как Boxfuse, который может помочь облегчить большую часть работы по созданию виртуальных машин и управлению ими; в противном случае потребуется много времени на выполнение работы, не очень связанной с основной деятельностью.

Итак, давайте взглянем на другой метод развертывания микросервисов, который по-прежнему имеет характеристики виртуальной машины, но является относительно легким.

## Режим одного экземпляра службы с одним контейнером

При использовании этого шаблона каждый экземпляр службы запускается в своем собственном контейнере. Контейнеры — это механизмы виртуализации, работающие на уровне операционной системы. Контейнер содержит несколько процессов, работающих в «песочнице». С точки зрения процесса, у них есть собственное пространство имен и корневая файловая система; Память контейнера и ресурсы ЦП могут быть ограничены. Некоторые контейнеры также имеют ограничения ввода-вывода, включая зоны Docker и Solaris.

Изображение ниже иллюстрирует этот шаблон:

![deployment-strategy-3](./images/deployment-strategy-3.png)

Использование этого шаблона требует упаковки службы в образ контейнера. Образ контейнера — это файловая система, содержащая библиотеки и приложения, необходимые для запуска службы. Некоторые образы контейнеров состоят из полной корневой файловой системы Linux, другие — облегченные. Например, чтобы развернуть службу Java, вам необходимо создать образ контейнера, содержащий среду выполнения Java, возможно, сервер Apache Tomcat, и скомпилированное приложение Java.

После того как служба упакована в образ контейнера, необходимо запустить несколько контейнеров. Как правило, для запуска нескольких контейнеров на физической или виртуальной машине может потребоваться система управления кластером, например k8s или Marathon, для управления контейнерами. Система управления кластером использует хост в качестве пула ресурсов и определяет, какой хост запланировать для контейнера, исходя из требований к ресурсам каждого контейнера.

Модель одного экземпляра службы с одним контейнером также имеет свои преимущества и недостатки. Преимущества контейнеров очень похожи на виртуальные машины. Экземпляры службы полностью независимы, а ресурсы, потребляемые каждым контейнером, можно легко отслеживать. Подобно виртуальным машинам, контейнеры используют технологию изоляции для развертывания сервисов. API управления контейнерами также может служить API для служб управления.

Однако, в отличие от виртуальных машин, контейнеры — это легкая технология. Образы контейнеров создаются быстро: например, упаковка приложения Spring Boot в образ контейнера занимает на ноутбуке всего 5 секунд. Поскольку механизм запуска операционной системы не требуется, контейнеры запускаются быстро. При запуске контейнера запускается фоновая служба.

Есть также некоторые недостатки использования контейнеров. Хотя контейнерная архитектура быстро развивается, она все еще не настолько развита, как архитектура виртуальных машин. А поскольку ядро ​​ОС хоста используется совместно контейнерами, оно не так безопасно, как виртуальная машина.

Кроме того, контейнерная технология выдвигает множество индивидуальных требований к управлению образами контейнеров. Если вы не используете Google Container Engine или Amazon EC2 Container Service (ECS), пользователям придется управлять как архитектурой контейнера, так и архитектурой виртуальных машин.

В-третьих, контейнеры часто развертываются в архитектурах, взимаемых на основе виртуальных машин. Очевидно, что клиенты также будут увеличивать затраты на развертывание, чтобы справиться с увеличением нагрузки.

Интересно, что различие между контейнерами и виртуальными машинами становится все более размытым. Как упоминалось ранее, виртуальные машины Boxfuse быстро запускаются и создаются, а технология Clear Container предназначена для создания облегченных виртуальных машин. Технология компаний-юникеров также привлекла всеобщее внимание. Docker недавно приобрел компанию Unikernel.

В дополнение к этому, технология бессерверного развертывания позволяет избежать вышеупомянутых недостатков технологий контейнеров и виртуальных машин и привлекает все больше и больше внимания. Давайте посмотрим ниже.

## Бессерверное развертывание

AWS Lambda — пример технологии бессерверного развертывания, поддерживающей сервисы Java, Node.js и Python; сервис необходимо упаковать в ZIP-файл и загрузить в AWS Lambda для развертывания. Могут быть предоставлены метаданные, содержащие имя функции, обрабатывающей запрос службы (событие). AWS Lambda автоматически запускает микросервисы, которые обрабатывают достаточное количество запросов, но оплата взимается только на основе времени работы и объема потребляемой памяти. Конечно, дьявол кроется в деталях, и у AWS Lambda тоже есть ограничения. Но никому не нужно беспокоиться о каких-либо аспектах серверов, виртуальных машин или контейнеров, которые просто интересны.

Лямбда-функции — это сервисы без сохранения состояния. Запросы обычно обрабатываются путем активации сервисов AWS. Например, когда изображение загружается в корзину S3 и активируется функция Lambda, вы можете вставить запись в таблицу изображений DynamoDB, опубликовать сообщение в потоке Kinesis и запустить действие по обработке изображения. Функции Lambda также можно активировать через сторонние веб-сервисы.

Существует четыре способа активировать функцию Lambda:

- Прямой способ, используя запрос веб-сервиса
- Автоматически реагировать на такие события, как AWS S3, DynamoDB, Kinesis или Simple Email Service.
- Автоматическая обработка HTTP-запросов от клиентов приложений через AWS API Gateway.
- Режим синхронизации, ответ через cron - очень похоже на режим таймера

Видно, что AWS Lambda — очень удобный способ развертывания микросервисов. Метод выставления счетов на основе запросов означает, что пользователям нужно нести только нагрузку по обработке своего собственного бизнеса; кроме того, поскольку им не нужно разбираться в инфраструктуре, пользователям нужно только разрабатывать свои собственные приложения.

Однако существует еще много ограничений. Его не нужно использовать для развертывания долгосрочных служб, таких как использование сообщений, пересылаемых со стороннего прокси-сервера. Запрос должен быть выполнен в течение 300 секунд. Сервис должен быть без сохранения состояния, поскольку теоретически AWS Lambda будет генерировать независимый экземпляр для каждого запроса; это должно быть сделано на поддерживаемом языке. Служба должна запуститься быстро, иначе она будет остановлена ​​по таймауту.
Развертывание приложений микросервисов также является непростой задачей. Существуют сотни сервисов, написанных на разных языках и фреймворках. Каждая служба представляет собой мини-приложение со своими уникальными требованиями к развертыванию, ресурсам, масштабированию и мониторингу. Существует несколько моделей развертывания микросервисов, включая один экземпляр одной виртуальной машины и один экземпляр одного контейнера. Другая альтернатива — AWS Lambda, бессерверный подход.
