### стратегия балансировки нагрузки dubbo

#### Случайный баланс нагрузки

По умолчанию dubbo — это RandomLoadBalance, что означает **случайные** вызовы для достижения балансировки нагрузки. Вы можете установить разные веса для разных экземпляров провайдера. Нагрузка будет сбалансирована в зависимости от веса. Чем больше вес, тем выше распределение трафика. Как правило, вы можете использовать это значение по умолчанию.

Идея алгоритма очень проста. Предположим, существует группа серверов server = `[A, B, C]`, их соответствующие веса — это веса = `[5, 3, 2]`, а сумма весов равна 10. Теперь разложите эти значения весов по одномерным значениям координат, интервал `[0, 5)` принадлежит серверу A, интервал `[5, 8)` принадлежит серверу B, а интервал `[8, 10)` принадлежит серверу C. Далее используйте случайный генератор чисел для генерации случайного числа в диапазоне `[0, 10)`, а затем расчета, на какой интервал попадет это случайное число. Например, число 3 попадет в диапазон, соответствующий серверу А. В это время просто вернитесь на сервер А. Чем больше вес машины, тем больше соответствующий диапазон интервалов на оси координат, поэтому числа, сгенерированные генератором случайных чисел, будут иметь большую вероятность попасть в этот интервал. Пока случайные числа, сгенерированные генератором случайных чисел, хорошо распределены, после множественного выбора доля выбираемых каждого сервера близка к его весовой пропорции. Например, после 10 000 выборов сервер A выбирается примерно 5 000 раз, сервер B выбирается примерно 3 000 раз, а сервер C выбирается примерно 2 000 раз.

#### RoundRobinLoadBalance

По умолчанию трафик распределяется на каждую машину равномерно, но если производительность каждой машины различна, можно легко сделать загрузку машины с низкой производительностью слишком высокой. Поэтому в это время необходимо отрегулировать вес, чтобы машины с низкой производительностью могли перевозить меньший вес и меньше проезжать.

При обращении за машинами к однокурсникам по эксплуатации и обслуживанию, иногда нам везет, и у компании бывает достаточно ресурсов. Только что была выпущена партия горячих, свежеподготовленных виртуальных машин, с относительно высокими конфигурациями: 8-ядерные машины + 16G, и мы подали заявку на 2 машины. Через некоторое время мы почувствовали, что двух машин недостаточно, поэтому я подошел к однокурснику по эксплуатации и обслуживанию и сказал: «Брат, можешь дать мне еще одну машину?» Но на этот раз осталась всего одна машина 4 ядра+8G. В это время вы можете установить вес 4 для двух 8-ядерных компьютеров 16G и вес 2 для оставшейся 4-ядерной машины 8G.

#### Наименьший активный баланс нагрузки

Объяснение `LeastActiveLoadBalance` на официальном сайте звучит так: «**Балансировка нагрузки по минимальному активному номеру**». Чем меньше количество активных вызовов, тем эффективнее работает поставщик услуг и может обрабатывать больше запросов в единицу времени. В настоящее время запросы сначала будут распределяться поставщику услуг.

Основная идея алгоритма балансировки минимальной активной нагрузки заключается в следующем:

Каждому поставщику услуг будет соответствовать активный номер `active`. Первоначально `active` равен 0 для всех поставщиков услуг. Всякий раз при получении запроса `active` соответствующего поставщика услуг будет увеличиваться на 1. После обработки запроса `active` будет уменьшаться на 1. Следовательно, если производительность поставщика услуг выше и эффективность обработки запросов выше, то `active` также будет уменьшаться быстрее. Следовательно, запросы могут быть предпочтительно распределены таким поставщикам услуг.

Конечно, помимо минимального активного числа, `LeastActiveLoadBalance` также вводит в реализацию весовые значения. Точнее, `LeastActiveLoadBalance` реализован на основе алгоритма взвешенного минимального активного числа.

#### ConsistentHashLoadBalance

Алгоритм согласованного хеширования, запросы с одинаковыми параметрами должны передаваться провайдеру. При зависании провайдера оставшийся трафик будет равномерно распределен по виртуальным узлам, и джиттер не будет слишком большим. **Если вам нужна не случайная балансировка нагрузки**, а все запросы одного типа идут на один узел, используйте эту стратегию последовательного хеширования.

> Более подробное описание стратегии балансировки нагрузки dubbo можно найти на официальном сайте https://dubbo.apache.org/zh/docs/advanced/loadbalance.

### стратегия отказоустойчивости кластера dubbo

#### Режим отказоустойчивого кластера

Автоматически включать сбой и автоматически повторять попытки на других машинах. Это значение **по умолчанию**, которое часто встречается в операциях чтения. (Если не удалось, повторите попытку на других машинах)

Количество повторов можно настроить следующими способами:

```xml
<dubbo:service retries="2" />
```

или

```xml
<dubbo:reference retries="2" />
```

или

```xml
<dubbo:reference>
    <dubbo:method name="findFoo" retries="2" />
</dubbo:reference>
```

#### Режим отказоустойчивого кластера

Если вызов не удался, он завершится неудачей немедленно. Это часто встречается в неидемпотентных операциях записи, таких как добавление новой записи (если вызов завершится неудачно, он завершится немедленно).

#### Режим отказоустойчивого кластера

Игнорировать исключения, когда они происходят, часто используемые для неважных вызовов интерфейса, таких как ведение журнала.

Пример конфигурации следующий:

```xml
<dubbo:service cluster="failsafe" />
```

или

```xml
<dubbo:reference cluster="failsafe" />
```

#### Режим отказоустойчивого кластера

Если запрос не удается, фон автоматически записывает запрос, а затем регулярно отправляет его повторно, что больше подходит для написания очередей сообщений.

#### Режим разветвления кластера

**Параллельный вызов нескольким поставщикам услуг** приведет к возврату немедленно, как только один из них будет успешным. Он часто используется для операций чтения с высокими требованиями к реальному времени, но при этом тратится больше ресурсов службы. Вы можете установить максимальное количество параллелизма с помощью `forks="2"`.

#### Режим широковещательного кластера

Обзвоните всех провайдеров по одному. Если какой-либо провайдер выйдет из строя, будет сообщено об ошибке (поддерживается начиная с версии `2.1.0`). Обычно используется для уведомления всех поставщиков о необходимости обновления информации о локальных ресурсах, такой как кеш или журналы.

> Более подробное описание стратегии отказоустойчивости кластера dubbo можно найти на официальном сайте https://dubbo.apache.org/zh/docs/advanced/fault-tolerent-strategy.

### стратегия динамического прокси dubbo

По умолчанию javassist используется для генерации динамического байт-кода и создания прокси-классов. Однако вы можете настроить свою собственную стратегию динамического прокси с помощью механизма расширения spi.
