### даббо поддерживает разные протоколы связи

- протокол даббо `dubbo://`

По умолчанию** используется протокол даббо, одно длинное соединение, асинхронная связь NIO и гессиан в качестве протокола сериализации. Сценарий использования: объем передаваемых данных невелик (каждый запрос находится в пределах 100 КБ), но объем параллелизма высок, а количество машин-потребителей услуг намного больше, чем количество машин поставщиков услуг.

Для поддержки сценариев с высоким уровнем параллелизма поставщики услуг обычно имеют всего несколько компьютеров, но потребители услуг имеют сотни компьютеров, а количество вызовов может достигать сотен миллионов в день! В настоящее время наиболее целесообразно использовать длинное соединение, которое должно поддерживать длительное соединение с каждым потребителем услуги, всего может быть 100 соединений. Кроме того, он напрямую основан на асинхронной связи NIO с длинным соединением, которая может поддерживать запросы с высоким параллелизмом.

Длительное соединение, с точки зрения непрофессионала, означает, что вы можете продолжать отправлять запросы после установления соединения без необходимости устанавливать другое соединение.

![dubbo-keep-connection](./images/dubbo-keep-connection.png)

Для коротких соединений соединение необходимо восстанавливать каждый раз перед отправкой запроса.

![dubbo-not-keep-connection](./images/dubbo-not-keep-connection.png)

- протокол RMI `rmi://`

Протокол RMI реализован с использованием стандартного JDK java.rmi.\*, с использованием блокировки коротких соединений и стандартных методов сериализации JDK. Множественные короткие соединения подходят для ситуаций, когда количество потребителей и поставщиков примерно одинаково. Они подходят для передачи файлов и, как правило, используются реже.

- гессенский протокол `hessian://`

Протокол Hessian 1 используется для интеграции служб Hessian. Нижний уровень Hessian использует HTTP-связь и сервлет для предоставления услуг. По умолчанию в Dubbo встроен Jetty как реализация сервера. Используйте протокол сериализации Hessian и несколько коротких соединений, что подходит для ситуаций, когда количество поставщиков превышает количество потребителей. Он подходит для передачи файлов и, как правило, используется реже.

- HTTP-протокол `http://`

Протокол удаленного вызова на основе формы HTTP, реализованный с использованием Spring HttpInvoker. Используйте сериализацию форм.

- протокол бережливости `thrift://`

Протокол thrift, поддерживаемый в настоящее время в dubbo, является расширением собственного протокола thrift. На основе собственного протокола добавляется некоторая дополнительная информация заголовка, такая как имя службы, магический номер и т. д.

- веб-сервис `webservice://`

Протокол удаленных вызовов на основе WebService, основанный на простом внешнем интерфейсе Apache CXF и реализации Transports-http. Используйте сериализацию текста SOAP.

- протокол memcached `memcached://`

Протокол RPC реализован на основе memcached.

- протокол Redis `redis://`

Протокол RPC реализован на базе Redis.

- протокол отдыха `rest://`

Поддержка вызовов REST на основе стандартного Java REST API — JAX-RS 2.0 (сокращение от Java API для веб-служб RESTful).

- протокол gPRC `grpc://`

Dubbo поддерживает протокол gRPC начиная с версии 2.7.5. Разработчики, которые планируют использовать связь HTTP/2 или хотят воспользоваться преимуществами Stream, противодавления, реактивного программирования и других возможностей, предоставляемых gRPC, могут рассмотреть возможность включения протокола gRPC.

### Протоколы сериализации, поддерживаемые dubbo

Dubbo поддерживает hession, двоичную сериализацию Java, json, текстовую сериализацию SOAP и несколько протоколов сериализации. Но гессиан — это протокол сериализации по умолчанию.

### Давайте поговорим о структуре данных Hessian

Механизм сериализации объектов Hessian имеет 8 примитивных типов:

- Необработанные двоичные данные
-логическое значение
- 64-битная дата (дата с 64-битным значением миллисекунды)
- 64-битный дубль
- 32-битное целое число
- 64-битная длина
-ноль
— строка в кодировке UTF-8.

Есть также 3 рекурсивных типа:

- list для списков и массивов
- карта для карт и словарей
- объект для объектов

Существует также специальный тип:

- ref: используется для представления ссылки на общий объект.

### Почему ПБ наиболее эффективно?

На самом деле, причина, по которой PB имеет такую ​​хорошую производительность, объясняется главным образом двумя причинами: **Во-первых**, он использует прото-компилятор для автоматической сериализации и десериализации, что происходит очень быстро. Он должен быть в `20~100` раз быстрее, чем `XML` и `JSON`; **Во-вторых**, эффект сжатия данных хороший, а это означает, что объем данных после сериализации невелик. Благодаря небольшому размеру пропускная способность и скорость передачи будут оптимизированы.
