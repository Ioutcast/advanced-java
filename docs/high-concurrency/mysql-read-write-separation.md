# Как реализовать разделение чтения/записи?

## Вопрос на собеседовании

Вы выполнили разделение чтения/записи MySQL? Как реализовать разделение чтения/записи MySQL? Каков принцип репликации master-slave MySQL? Как решить проблему задержки синхронизации master-slave MySQL?

## Что хочет знать интервьюер

На этапе высокого параллелизма необходимо выполнить разделение чтения/записи. Что это значит? Потому что на самом деле большинство интернет-компаний, некоторых веб-сайтов или приложений на самом деле читают больше и пишут меньше. Итак, для этой ситуации мы пишем основную библиотеку, но основная библиотека зависает из нескольких подчиненных библиотек, а затем читает из нескольких подчиненных библиотек. Разве он не сможет поддерживать более высокую нагрузку на одновременное чтение?

## Анализ вопросов на собеседовании

### Как реализовать разделение чтения/записи в MySQL?

На самом деле, это очень просто. Он основан на архитектуре репликации «главный-подчиненный». Проще говоря, мы создаем главную базу данных и подключаем несколько подчиненных баз данных. Дальше мы пишем только в главную базу данных, а затем главная база данных автоматически синхронизирует данные с подчиненной базой данных.

### Каков принцип репликации master-slave MySQL?

Основная библиотека записывает изменения в журнал binlog, а затем, после того как ведомая библиотека подключается к основной библиотеке, ведомая библиотека имеет поток ввода-вывода, копирует журнал binlog основной библиотеки в свой локальный файл и записывает его в журнал ретрансляции. Затем в подчиненной библиотеке есть поток SQL, который будет читать binlog из журнала реле, а затем выполнять содержимое журнала binlog, то есть снова выполнять SQL локально, чтобы гарантировать, что данные между ним и основной библиотекой совпадают.

![mysql-master-slave](./images/mysql-master-slave.png)

Очень важным моментом здесь является то, что процесс синхронизации данных основной библиотеки с подчиненной библиотекой сериализуется, а это значит, что параллельные операции над основной библиотекой будут выполняться последовательно над подчиненной библиотекой. Так что это очень важный момент. Из-за особенностей копирования журналов ведомой библиотеки из основной библиотеки и последовательного выполнения SQL в сценарии с высоким параллелизмом данные из ведомой библиотеки определенно будут медленнее, чем данные из основной библиотеки, которая **задерживается**. Поэтому часто случается, что только что записанные в основную базу данные могут быть не прочитаны, и на их чтение уйдут десятки миллисекунд, а то и сотни миллисекунд.

И здесь есть еще одна проблема, то есть, если основная база данных вдруг выйдет из строя, а данные еще не синхронизировались с подчиненной базой данных, то некоторые данные могут быть недоступны на подчиненной базе данных, а часть данных может быть потеряна.

Таким образом, MySQL на самом деле имеет два механизма в этой области: один — **полусинхронная репликация**, которая используется для решения проблемы потери данных в основной базе данных; другой — **параллельная репликация**, которая используется для решения проблемы задержки синхронизации между главным и подчиненным устройствами.

Эта так называемая **полусинхронная репликация**, также называемая репликацией `semi-sync`, означает, что после того, как главная библиотека записывает журнал binlog, она будет **принуждена** немедленно синхронизировать данные с ведомой библиотекой. После того как ведомая библиотека запишет журнал в свой локальный журнал ретрансляции, она вернет подтверждение главной библиотеке. Главная библиотека будет считать операцию записи завершенной только после получения **хотя бы одного подтверждения от ведомой библиотеки**.

Так называемая **параллельная репликация** подразумевает запуск нескольких потоков из библиотеки, параллельное чтение журналов разных библиотек в журнале ретрансляции, а затем **параллельное воспроизведение журналов разных библиотек**. Это параллелизм на уровне библиотеки.

### Проблема задержки синхронизации master-slave MySQL (суть)

В прошлом онлайн-ошибки, вызванные задержкой синхронизации между главным и подчиненным устройствами, действительно устранялись онлайн, что представляло собой небольшие производственные аварии.

Это сцена? Одноклассник пишет такую ​​логику кода. Сначала вставьте фрагмент данных, затем проверьте его, а затем обновите данные. В пиковый период производственной среды скорость одновременной записи достигала 2000/с. В это время задержка репликации master-slave, вероятно, составляла несколько десятков миллисекунд. В Интернете вы обнаружите, что каждый день всегда есть какие-то данные. Мы ожидаем обновления некоторых важных данных, но они не обновляются в периоды пиковой нагрузки. Пользователи оставляют отзывы в службу поддержки клиентов, а служба поддержки клиентов оставляет отзывы нам.

Передаем команду MySQL:

```sql
show slave status
```

Глядя на `Seconds_Behind_Master`, можно увидеть, что данные, скопированные из подчиненной библиотеки в основную, отстают на несколько мс.

Вообще говоря, если задержка «главный-подчиненный» серьезная, есть следующие решения:

- Разделение базы данных, разделение одной основной базы данных на несколько основных баз данных, параллельная запись каждой основной базы данных снижается в несколько раз, а задержка master-slave в это время незначительна.
- Включите параллельную репликацию, поддерживаемую MySQL, и несколько библиотек можно будет реплицировать параллельно. Если параллельная запись определенной библиотеки особенно высока, а параллельная запись одной библиотеки достигает 2000/с, параллельная репликация по-прежнему бессмысленна.
