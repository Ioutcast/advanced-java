# Архитектура Redis master-slave

Количество запросов в секунду, которое может выполнять автономный Redis, варьируется от десятков тысяч до десятков тысяч. Что касается кешей, они обычно используются для поддержки высокого параллелизма чтения. Таким образом, архитектура превращается в архитектуру «главный-подчиненный» с одним главным и несколькими подчиненными устройствами. Главный отвечает за запись и копирование данных на другие подчиненные узлы, а подчиненные узлы отвечают за чтение. Все запросы на чтение передаются подчиненному узлу. Это также позволяет легко добиться горизонтального расширения, **поддерживая чтение с высоким уровнем параллелизма**.

![Redis-master-slave](./images/redis-master-slave.png)

Репликация Redis -> архитектура «главный-подчиненный» -> разделение чтения/записи -> горизонтальное расширение для поддержки высокого одновременного чтения.

## Основной механизм репликации Redis

— Redis использует **асинхронный режим** для копирования данных на подчиненный узел. Однако, начиная с Redis 2.8, подчиненный узел каждый раз будет периодически подтверждать объем копируемых данных;
- Главный узел может быть сконфигурирован с несколькими подчиненными узлами;
- Ведомый узел также может подключаться к другим подчиненным узлам;
- При репликации подчиненного узла он не будет блокировать нормальную работу главного узла;
— Когда подчиненный узел реплицируется, он не блокирует свои собственные операции запроса. Он будет использовать старый набор данных для предоставления услуг; но когда репликация завершена, необходимо удалить старый набор данных и загрузить новый набор данных. В это время внешняя служба будет приостановлена;
- Подчиненный узел в основном используется для горизонтального расширения и разделения чтения/записи. Расширенный подчиненный узел может улучшить пропускную способность чтения.

Обратите внимание: если используется архитектура «главный-подчиненный», рекомендуется включить [упорство](./redis-persistence.md) главного узла. Не рекомендуется использовать подчиненный узел в качестве горячего резервного копирования данных главного узла, поскольку в этом случае, если вы отключите постоянство главного узла, данные могут оказаться пустыми при сбое и перезапуске главного узла, а затем данные подчиненного узла могут быть потеряны после репликации.

Кроме того, необходимо реализовать различные планы резервного копирования для главного устройства. В случае потери всех локальных файлов выберите RDB из резервной копии для восстановления главного, чтобы обеспечить наличие данных при запуске. Даже если подчиненный узел может автоматически взять на себя управление главным узлом, как описано ниже, главный узел может автоматически перезапуститься до того, как Sentinel обнаружит сбой главного узла, что все равно может привести к удалению всех вышеуказанных данных подчиненного узла.

## Основной принцип репликации Master-Slave Redis

Когда подчиненный узел запускается, он отправляет команду `PSYNC` главному узлу.

Если это первый раз, когда подчиненный узел подключается к главному узлу, будет запущена полная репликация `full resynchronization`. В это время мастер запустит фоновый поток и начнет генерировать файл моментального снимка `RDB`. При этом все вновь полученные команды записи от клиента будут кэшироваться в памяти. После создания файла `RDB` ведущий отправит этот `RDB` ведомому устройству. Ведомый сначала запишет его на локальный диск, а затем загрузит с локального диска в память. Затем мастер отправит команду записи, кэшированную в памяти, ведомому, а ведомый также синхронизирует данные. Если у подчиненного узла произошел сбой в сети с главным узлом и он отключен, он автоматически подключится заново. После подключения главный узел лишь скопирует недостающие данные на слейв.

### Возобновление загрузки точки останова репликации «главный-подчиненный»

Начиная с Redis 2.8, для возобновленных загрузок поддерживается репликация «главный-подчиненный». Если сетевое соединение разорвано во время процесса репликации «главный-подчиненный», вы можете продолжить копирование с того места, где вы его последний раз копировали, вместо того, чтобы начинать с нуля.

Главный узел будет поддерживать резерв в памяти. И ведущий, и ведомый сохранят смещение реплики и идентификатор главного запуска. Смещение сохраняется в резервной памяти. Если сетевое соединение между главным и подчиненным устройством разорвано, подчиненное устройство позволит главному устройству продолжить репликацию со смещения последней реплики. Если соответствующее смещение не найдено, то будет выполнено `resynchronization`.

> Обнаружение главного узла на основе хост+IP ненадежно. Если главный узел перезапускается или данные изменяются, подчиненные узлы следует различать по разным идентификаторам запуска.

### Бездисковая репликация

Мастер создает `RDB` непосредственно в памяти, а затем отправляет его ведомому. Он не будет сохранен локально на диске. Просто включите `repl-diskless-sync yes` в файле конфигурации.

```bash
repl-diskless-sync yes

# 等待 5s 后再开始复制，因为要等更多 slave 重新连接过来
repl-diskless-sync-delay 5
```

### Обработка ключа с истекшим сроком действия

Ведомое устройство не истечет срок действия ключа, а будет только ждать, пока у ведущего истечет срок действия ключа. Если у ведущего истекает срок действия ключа или он удаляется через LRU, команда del будет смоделирована и отправлена ​​ведомому устройству.

## Завершить процесс копирования

Когда подчиненный узел запускается, он сохраняет информацию главного узла локально, включая `host` и `ip` главного узла, но процесс репликации не запускается.

Внутри подчиненного узла есть запланированная задача, которая каждую секунду проверяет, есть ли новый главный узел для подключения и копирования. Если он найден, он устанавливает сетевое соединение с главным узлом. Затем подчиненный узел отправляет команду `ping` главному узлу. Если ведущий устанавливает requirepass, ведомый узел должен отправить пароль masterauth для аутентификации. Главный узел **выполняет полную репликацию** в первый раз и отправляет все данные подчиненному узлу. В дальнейшем главный узел продолжает асинхронно копировать команды записи на подчиненный узел.

![Redis-master-slave-replication-detail](./images/redis-master-slave-replication-detail.png)

### Полная копия

- Мастер выполняет команду bgsave для локального создания файла моментального снимка rdb.
- Главный узел отправляет файл моментального снимка rdb подчиненному узлу. Если время копирования rdb превышает 60 секунд (repl-timeout), то подчиненный узел будет считать копирование неудавшимся, и вы можете соответствующим образом увеличить этот параметр (для машин с гигабитными сетевыми картами обычно в секунду передаются файлы 100 МБ, 6G, что, вероятно, превысит 60 с).
— Когда главный узел генерирует rdb, он кэширует все новые команды записи в памяти. После того как ведомый узел сохранит базу данных, он скопирует новые команды записи на ведомый узел.
- Если во время копирования буфер памяти постоянно занимает более 64 МБ или превышает 256 МБ за один раз, копирование остановится и копирование завершится неудачей.

```bash
client-output-buffer-limit slave 256MB 64MB 60
```

- После того как подчиненный узел получает rdb, он очищает свои старые данные, а затем перезагружает rdb в свою память. Обратите внимание, что перед очисткой старых данных ведомый узел по-прежнему будет предоставлять внешние услуги на основе старой версии данных.
- Если AOF включен на подчиненном узле, BGREWRITEAOF будет выполнен немедленно для перезаписи AOF.

### Инкрементное копирование

- Если сетевое соединение «главный-подчиненный» разорвано во время полной репликации, инкрементная репликация будет запущена, когда подчиненное устройство снова подключится к главному.
- Мастер напрямую получает часть потерянных данных из собственного резерва и отправляет их подчиненному узлу. Размер отставания по умолчанию составляет 1 МБ.
- Ведущий получает данные из резервной копии на основе смещения в psync, отправленном ведомым.

### сердцебиение

Главный и подчиненный узлы будут отправлять друг другу контрольные сообщения.

По умолчанию ведущий отправляет контрольные сигналы каждые 10 секунд, а подчиненный узел отправляет контрольные сигналы каждые 1 секунду.

### Асинхронная репликация

Каждый раз, когда ведущий получает команду записи, он сначала записывает данные внутрь, а затем асинхронно отправляет их подчиненному узлу.

## Как Redis может добиться высокой доступности?

Если система может предоставлять услуги внешнему миру в 99,99% случаев в течение 365 дней, то говорят, что система имеет высокую доступность.

Если один из подчиненных устройств зависнет, это не повлияет на доступность. Существуют и другие подчиненные устройства, предоставляющие ту же службу внешних запросов с теми же данными.

Но что произойдет, если главный узел умрет? Нет возможности записать данные. При записи в кэш все невалидно. Какая польза от подчиненных узлов? Без мастера, который копирует в них данные, система эквивалентна недоступности.

Архитектура высокой доступности Redis называется `failover` **отработка отказа**, которую также можно назвать переключением активный-резервный.

При выходе из строя главного узла он автоматически обнаруживает и автоматически переключает подчиненный узел на главный узел. Этот процесс называется переключением главный-резервный. Этот процесс обеспечивает высокую доступность в рамках архитектуры Redis «главный-подчиненный».

Redis [Высокая доступность на базе Sentinel](./redis-sentinel.md) будет подробно объяснен позже.
