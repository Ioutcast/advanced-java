# Как обеспечить надежную передачу сообщений?

## Вопрос на собеседовании

Как обеспечить надежную передачу сообщений? Другими словами, как решить проблему потери сообщений?

## Что хочет знать интервьюер

Это точно. При использовании MQ существует основной принцип: не может быть ни на один фрагмент данных больше, ни на один фрагмент данных меньше. Большего быть не может, о чем я упоминал ранее [Повторное потребление и идемпотентные проблемы](./how-to-ensure-that-messages-are-not-repeatedly-consumed.md). Меньше быть не может, а значит не потеряйте эти данные. Тогда вам стоит задуматься над этим вопросом.

Если вы используете MQ для доставки очень важных сообщений, таких как сообщения о выставлении счетов и вычетов, вы должны гарантировать, что сообщения о выставлении счетов никогда не будут потеряны в процессе доставки MQ.

## Анализ вопросов на собеседовании

Проблемы с потерей данных могут возникнуть у производителей, MQ и потребителей. Давайте проанализируем их из RabbitMQ и Kafka соответственно.

### КроликMQ

![rabbitmq-message-lose](./images/rabbitmq-message-lose.png)

#### Производитель потерял данные

Когда производитель отправляет данные в RabbitMQ, данные могут быть потеряны на полпути из-за проблем в сети или других проблем.

На данный момент вы можете использовать функцию транзакции, предоставляемую RabbitMQ, то есть производитель запускает транзакцию RabbitMQ `channel.txSelect()` перед отправкой данных, а затем отправляет сообщение. Если сообщение не будет успешно получено RabbitMQ, производитель получит ошибку исключения. В это время транзакцию `channel.txRollback()` можно откатить, а затем отправить сообщение повторно; если сообщение получено, транзакция `channel.txCommit()` может быть отправлена.

```java
try {
    // 通过工厂创建连接
    connection = factory.newConnection();
    // 获取通道
    channel = connection.createChannel();
    // 开启事务
    channel.txSelect();

    // 这里发送消息
    channel.basicPublish(exchange, routingKey, MessageProperties.PERSISTENT_TEXT_PLAIN, msg.getBytes());

    // 模拟出现异常
    int result = 1 / 0;

    // 提交事务
    channel.txCommit();
} catch (IOException | TimeoutException e) {
    // 捕捉异常，回滚事务
    channel.txRollback();
}
```

Но проблема в том, что как только будет реализован механизм транзакций RabbitMQ (синхронизация), пропускная способность в основном снизится, поскольку она потребляет слишком много производительности.

Вообще говоря, если вы хотите гарантировать, что сообщения, записанные в RabbitMQ, не будут потеряны, вы можете включить режим `confirm`. После установки режима `confirm` на продюсере каждому написанному вами сообщению будет присвоен уникальный идентификатор. Затем, если оно будет записано в RabbitMQ, RabbitMQ отправит вам ответное сообщение `ack`, чтобы сообщить вам, что с сообщением все в порядке. Если RabbitMQ не сможет обработать сообщение, он перезвонит одному из ваших интерфейсов `nack`, чтобы сообщить вам, что прием сообщения не удался, и вы можете повторить попытку. И вы можете объединить этот механизм для сохранения статуса каждого идентификатора сообщения в памяти. Если вы не получили обратного вызова на это сообщение по истечении определенного периода времени, вы можете отправить его повторно.

Самая большая разница между механизмом транзакций и механизмом `confirm` заключается в том, что **механизм транзакций является синхронным**. После того как вы отправите транзакцию, она будет **заблокирована**, но механизм `confirm` является **асинхронным**. После отправки сообщения вы можете отправить следующее сообщение, а затем, после получения сообщения, RabbitMQ асинхронно перезвонит одному из ваших интерфейсов, чтобы уведомить вас о получении сообщения.

Поэтому механизм `confirm` обычно используется, чтобы избежать потери данных на стороне производителя.

> Канал, который уже находится в режиме транзакции, не может быть установлен в режим подтверждения, то есть эти два режима не могут сосуществовать.

Существует три способа реализации производителей `confirm` на стороне клиента:

1. **Обычный режим подтверждения**: после отправки каждого сообщения вызывайте метод `waitForConfirms()` и ждите подтверждения от сервера. Если сервер возвращает false или не возвращает сообщение в течение определенного периода времени, клиент может повторно отправить сообщение.

```java
channel.basicPublish(ConfirmConfig.exchangeName, ConfirmConfig.routingKey, MessageProperties.PERSISTENT_TEXT_PLAIN, ConfirmConfig.msg_10B.getBytes());
if (!channel.waitForConfirms()) {
    // 消息发送失败
    // ...
}
```

2.**Режим пакетного подтверждения**: после отправки каждого пакета сообщений вызывайте метод `waitForConfirms()` и ждите подтверждения от сервера.

```java
channel.confirmSelect();
for (int i = 0; i < batchCount; ++i) {
    channel.basicPublish(ConfirmConfig.exchangeName, ConfirmConfig.routingKey, MessageProperties.PERSISTENT_TEXT_PLAIN, ConfirmConfig.msg_10B.getBytes());
}
if (!channel.waitForConfirms()) {
    // 消息发送失败
    // ...
}
```

3. **Асинхронный режим подтверждения**: укажите метод обратного вызова. Клиент вызовет этот метод обратно после того, как сервер подтвердит одно или несколько сообщений.

```java
SortedSet<Long> confirmSet = Collections.synchronizedSortedSet(new TreeSet<Long>());
channel.confirmSelect();
channel.addConfirmListener(new ConfirmListener() {
    public void handleAck(long deliveryTag, boolean multiple) throws IOException {
        if (multiple) {
            confirmSet.headSet(deliveryTag + 1).clear();
        } else {
            confirmSet.remove(deliveryTag);
        }
    }

    public void handleNack(long deliveryTag, boolean multiple) throws IOException {
        System.out.println("Nack, SeqNo: " + deliveryTag + ", multiple: " + multiple);
        if (multiple) {
            confirmSet.headSet(deliveryTag + 1).clear();
        } else {
            confirmSet.remove(deliveryTag);
        }
    }
});

while (true) {
    long nextSeqNo = channel.getNextPublishSeqNo();
    channel.basicPublish(ConfirmConfig.exchangeName, ConfirmConfig.routingKey, MessageProperties.PERSISTENT_TEXT_PLAIN, ConfirmConfig.msg_10B.getBytes());
    confirmSet.add(nextSeqNo);
}
```

#### RabbitMQ потерял данные

Это означает, что сам RabbitMQ потерял данные. Для этого вы должны **включить постоянство RabbitMQ**, то есть сообщение будет сохраняться на диске после записи. Даже если сам RabbitMQ зависнет, **ранее сохраненные данные будут автоматически прочитаны после восстановления**, и, как правило, данные не будут потеряны. Если только не случается крайне редко, когда RabbitMQ выходит из строя до того, как он сохраняется, это может привести к небольшой потере данных, но вероятность мала.

Чтобы настроить постоянство, необходимо выполнить **два шага**:

— Установите постоянную очередь при ее создании. Это гарантирует, что RabbitMQ сохранит метаданные очереди, но не сохранит данные в очереди.

- Второй вариант — установить для `deliveryMode` сообщения значение 2 при отправке сообщения. Просто установите сообщение как постоянное, и RabbitMQ сохранит его на диске.

Эти два персистентности должны быть настроены одновременно. Даже если RabbitMQ зависнет и снова перезапустится, очередь восстановления будет перезапущена с диска, и данные в очереди будут восстановлены.

Обратите внимание: даже если вы включите механизм сохранения для RabbitMQ, существует вероятность того, что сообщение будет записано в RabbitMQ, но не успеет сохраниться на диске. К сожалению, RabbitMQ в это время зависает, что приведет к потере небольшого количества данных в памяти.

Следовательно, персистентность можно комбинировать с механизмом `confirm` на стороне производителя. Только после того, как сообщение будет сохранено на диске, производитель будет уведомлен о `ack`. Следовательно, даже если RabbitMQ зависает и данные теряются до того, как сообщение сохраняется на диске, и производитель не может получить `ack`, вы можете повторно отправить его самостоятельно.

#### Потребитель потерял данные

Если RabbitMQ теряет данные, то это главным образом потому, что когда вы их потребляете, они только что были использованы и еще не обработаны. В результате процесс зависает, типа перезапуска, что смущает. RabbitMQ думает, что вы его израсходовали, и данные теряются.

На данный момент вам необходимо использовать механизм `ack`, предоставляемый RabbitMQ. Проще говоря, вы должны отключить автоматический `ack` RabbitMQ. Вы можете просто вызвать его через API, а затем каждый раз, когда вы убедитесь, что обработка завершена в вашем собственном коде, вы можете `ack` в программе. В этом случае, если вы еще не закончили обработку, не будет ли `ack`? Тогда RabbitMQ подумает, что вы не закончили его обработку. В это время RabbitMQ выделит потребление другим потребителям для обработки, и сообщение не будет потеряно.

> Чтобы гарантировать, что сообщения из очереди надежно доходят до потребителей, RabbitMQ предоставляет механизм подтверждения сообщений. Потребитель может указать параметр noAck при объявлении очереди. Когда noAck=false, RabbitMQ будет ждать, пока потребитель явно отправит обратно сигнал подтверждения, прежде чем удалять сообщение из памяти (и диска, если это постоянное сообщение). В противном случае RabbitMQ удалит сообщение из очереди, как только оно будет использовано потребителем.

### Кафка

#### Потребитель потерял данные

Единственная ситуация, которая может привести к потере данных потребителем, — это то, что вы потребляете сообщение, а затем потребитель автоматически отправляет смещение, заставляя Kafka думать, что вы использовали сообщение, но на самом деле вы только что подготовились к обработке сообщения, и прежде чем обработать его, вы кладете трубку, и сообщение теряется.

Разве это не похоже на RabbitMQ? Всем известно, что Kafka автоматически отправляет смещения, поэтому, если вы **отключаете автоматическую отправку** смещений и отправляете смещения вручную после обработки, вы можете быть уверены, что данные не будут потеряны. Но это правда, что в это время может произойти повторное потребление. Например, если вы только что закончили обработку и еще не отправили смещение, а затем положили трубку, вы обязательно воспользуетесь им снова в это время, поэтому просто обеспечьте идемпотентность.

Проблема, возникающая в производственной среде, заключается в том, что после того, как наш потребитель Kafka потребляет данные, он записывает их в очередь памяти и сначала буферизует. В результате иногда вы просто записываете сообщение в очередь памяти, а затем потребитель автоматически отправляет смещение. Тогда, когда мы в это время перезапустим систему, данные в очереди памяти будут потеряны до того, как успеют обработаться.

#### Кафка потерял данные

Распространенным сценарием в этой области является то, что брокер Kafka выходит из строя, а затем лидер раздела переизбирается. Подумайте об этом: если у других последователей есть какие-то данные, которые в это время не синхронизированы, и лидер вешает трубку, то после выбора последователя, который станет лидером, не будут ли некоторые данные отсутствовать? Это приведет к потере некоторых данных.

Мы с этим тоже сталкивались в производственной среде, и тоже сталкивались. Лидерская машина Кафки раньше вышла из строя. После переключения ведомого на лидера мы обнаружим, что данные потеряны.

Поэтому на данный момент обычно требуется установить как минимум следующие четыре параметра:

- Установите для темы параметр `replication.factor`: это значение должно быть больше 1, а в каждом разделе должно быть не менее 2 копий.
- Установите параметр `min.insync.replicas` на сервере Kafka: это значение должно быть больше 1. Это требует от лидера, по крайней мере, ощущения, что хотя бы один ведомый все еще находится в контакте с самим собой и не отстает. Это может гарантировать, что после смерти лидера останется последователь.
- Установите `acks=all` на стороне производителя: это требует, чтобы каждый фрагмент данных был записан во все реплики, прежде чем его можно будет считать успешным.
- Установите `retries=MAX` на стороне производителя (очень, очень, очень большое значение, означающее неограниченное количество повторов): это требование для бесконечных повторов в случае сбоя записи, и оно застряло здесь.

Наша производственная среда настроена в соответствии с вышеуказанными требованиями. После этой настройки, по крайней мере, на стороне брокера Kafka, можно гарантировать, что в случае сбоя брокера лидера и переключения лидера данные не будут потеряны.

#### Потеряет ли производитель данные?

Если вы установите `acks=all` по вышеизложенной идее, то он точно не потеряется. Требуется, чтобы ваш лидер получил сообщение и все последователи синхронизировали сообщение, прежде чем запись будет считаться успешной. Если это условие не выполнено, производитель будет автоматически и непрерывно повторять попытки неограниченное количество раз.

### RocketMQ

#### Сценарий потери сообщения

1. Производитель может потерять сообщение при отправке его в MQ.
2. После того как MQ получит сообщение и запишет его на жесткий диск, сообщение может быть потеряно.
3. После записи сообщения на жесткий диск жесткий диск повреждается и сообщение теряется.
4. Потребители также могут терять сообщения при использовании MQ.
5. Весь узел MQ зависает и сообщения теряются.

#### Как производитель гарантирует, что сообщения не будут потеряны при их отправке?

Чтобы решить проблему потери сообщений при отправке, вы можете использовать собственный механизм **транзакционного сообщения** RocketMQ.

Принцип сообщения транзакции: сначала производитель отправляет **половину сообщения** (инкапсуляцию исходного сообщения), которая невидима для потребителя. MQ возвращает статус принятия сообщения через механизм ACK. Производитель выполняет локальную транзакцию и возвращает статус MQ (Commit, RollBack и т. д.). Если это Commit, MQ отправит сообщение в нисходящий поток. Если это RollBack, сообщение будет отброшено. Если статус Неизвестен, через некоторое время будет проверен статус локальной транзакции. По умолчанию проверка производится 15 раз, если она остается в состоянии «Неизвестно», это сообщение будет отброшено.

Зачем сначала отправлять половину сообщения? Цель состоит в том, чтобы сначала определить, есть ли проблема с MQ и нормально ли работает служба.

#### Как MQ может гарантировать, что сообщения не будут потеряны после их записи на жесткий диск?

Сохранение данных обходит кэш и меняется на синхронную очистку. На этом этапе необходимо изменить файл конфигурации брокера и изменить для параметраlushDiskType стратегию синхронной очистки SYNC_FLUSH. По умолчанию используется асинхронная очистка ASYNC_FLUSH. После успешного завершения синхронной очистки необходимо гарантировать, что сообщение сохранилось на диске.

#### После записи сообщения на жесткий диск, как гарантировать, что оно не будет потеряно в случае повреждения жесткого диска?

Чтобы гарантировать, что данные будут потеряны из-за повреждения диска, RocketMQ использует механизм «главный-подчиненный» и развертывание кластера. Данные в ведущем устройстве резервируются на нескольких ведомых устройствах, чтобы предотвратить потерю данных, вызванную отдельными точками сбоя.

Что делать, если главный узел не работает? DLedger появляется после зависания Мастер-ноды.

- Возьмите на себя управление журналом фиксации MQ.
-Выбрать подчиненные узлы
- Статус незафиксированной копии файла обычно меняется на зафиксированный после получения от узла.

#### Как потребители могут гарантировать, что потребление MQ не будет потеряно?

1. Если потребление не удалось из-за проблем с сетью, можно реализовать механизм повторной попытки. По умолчанию каждое сообщение будет повторено 16 раз.
2. Сбой многопоточного асинхронного потребления. MQ считает, что потребление прошло успешно, но на самом деле сообщение не дошло до бизнес-логики. Решение состоит в том, чтобы сначала выполнить локальную транзакцию, а затем вернуть статус успеха, как рекомендует MQ.

#### Как гарантировать, что весь узел MQ не потерян?

В этом крайнем случае, после того как сообщение не удалось отправить, его можно сначала сохранить локально, например, в кеше, а затем запустить другой поток для сканирования кэшированного сообщения и повторной попытки отправки.
