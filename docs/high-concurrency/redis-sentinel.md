# Кластер Redis Sentinel обеспечивает высокую доступность

## Знакомство с Sentinel

Sentinel, китайское название Sentinel. Sentinel — очень важный компонент кластерной архитектуры Redis. В основном он имеет следующие функции:

- Мониторинг кластера: отвечает за мониторинг правильности работы главного и подчиненного процессов Redis.
- Уведомление о сообщении: в случае сбоя экземпляра Redis Sentinel несет ответственность за отправку сообщений в виде уведомлений о тревогах администратору.
- Аварийное переключение: если главный узел зависает, он автоматически переносится на подчиненный узел.
- Центр конфигурации: в случае аварийного переключения уведомите клиента о новом главном адресе.

Sentinel используется для достижения высокой доступности кластеров Redis. Он также распространяется. Он работает как кластер Sentinel и работает вместе друг с другом.

— Во время аварийного переключения для определения того, отключен ли главный узел, требуется согласие большинства Sentinels, что включает в себя проблему распределенных выборов.
— Даже если некоторые узлы Sentinel не работают, кластер Sentinel все равно может нормально работать, потому что, если система аварийного переключения, которая сама по себе является важной частью механизма высокой доступности, будет одной точкой, это будет очень запутанно.

## Основные знания Sentinel

- Для обеспечения надежности Sentinel требуется как минимум 3 экземпляра.
— Архитектура развертывания «главный-подчиненный» Sentinel + Redis не гарантирует нулевую потерю данных, а может гарантировать только высокую доступность кластера Redis.
- Для сложной архитектуры развертывания главного-подчиненного устройства Sentinel + Redis постарайтесь провести достаточное тестирование и тренировки как в тестовой, так и в производственной среде.

Кластер Sentinel должен развернуть более двух узлов. Если кластер Sentinel развертывает только 2 экземпляра Sentinel, кворум = 1.

```
+----+         +----+
| M1 |---------| R1 |
| S1 |         | S2 |
+----+         +----+
```

Настройте `quorum=1`. Если мастер выходит из строя, пока один Sentinel в s1 и s2 думает, что мастер не работает, он может переключиться. В то же время s1 и s2 выберут Sentinel для выполнения аварийного переключения. Но в то же время в это время необходимо большинство, то есть большинство Стражей баллотируются.

```
2 个哨兵，majority=2
3 个哨兵，majority=2
4 个哨兵，majority=2
5 个哨兵，majority=3
...
```

Если в данный момент не работает только процесс M1, а Sentinel s1 работает нормально, то отработка отказа в порядке. Но если вся машина, на которой работают M1 и S1, выйдет из строя, то останется только один Sentinel, и не будет большинства, позволяющего выполнить аварийное переключение. Несмотря на то, что на другой машине есть маршрутизатор R1, отработка отказа не будет выполнена.

Классический трехузловой кластер Sentinel выглядит так:

```
       +----+
       | M1 |
       | S1 |
       +----+
          |
+----+    |    +----+
| R2 |----+----| R3 |
| S2 |         | S3 |
+----+         +----+
```

Конфигурация `quorum=2`, если машина, на которой находится М1, не работает, то из трёх Стражей осталось 2. S2 и S3 могут договориться о том, что главный узел отключен, а затем выбрать один из них для выполнения аварийного переключения. В то же время большинство из 3 Sentinels — это 2, поэтому оставшиеся 2 Sentinels работают, и можно разрешить аварийное переключение.

## Проблема потери данных при переключении Redis Sentinel в активный/резервный режим.

### Две ситуации, приводящие к потере данных

Процесс переключения активный/резервный режим может привести к потере данных:

- Потеря данных из-за асинхронной репликации.

Поскольку репликация главный->подчиненный является асинхронной, некоторые данные могут не быть скопированы на подчиненное устройство до сбоя главного устройства, и эта часть данных будет потеряна.

![async-replication-data-lose-case](./images/async-replication-data-lose-case.png)

- Потеря данных из-за разделения мозга

Split-brain, то есть машина, на которой находится определенный мастер, внезапно выходит из обычной сети и не может соединиться с другими подчиненными машинами, но на самом деле мастер все еще работает. В это время Sentinel может **подумать**, что главный сервер не работает, а затем начать выборы и переключить на него других подчиненных устройств. В это время в кластере будет два мастера, что представляет собой так называемый **разделённый мозг**.

Хотя ведомое устройство в это время переключено на ведущее устройство, клиент может не успеть переключиться на новое ведущее устройство и продолжает записывать данные на старое ведущее устройство. Поэтому при повторном восстановлении старого мастера он будет подвешен к новому мастеру как слейв, его собственные данные будут очищены, а данные снова скопированы с нового мастера. У нового мастера нет данных, записанных клиентом позже, поэтому эта часть данных теряется.

![Redis-cluster-split-brain](./images/redis-cluster-split-brain.png)

### Решения проблем с потерей данных

Настройте следующим образом:

```bash
min-slaves-to-write 1
min-slaves-max-lag 10
```

Указывает, что требуется как минимум 1 ведомое устройство, а задержка репликации и синхронизации данных не может превышать 10 секунд.

Если задержка репликации и синхронизации данных для всех слейвов превысит 10 секунд, то в это время мастер больше не будет получать никаких запросов.

- Уменьшить потери асинхронно реплицируемых данных.

С помощью конфигурации `min-slaves-max-lag` можно гарантировать, что, если ведомое устройство копирует данные, а задержка подтверждения слишком велика, считается, что слишком много данных может быть потеряно после выхода из строя ведущего устройства, и запрос на запись отклоняется. Это может уменьшить потери данных, вызванные тем, что некоторые данные не синхронизируются с ведомым устройством при выходе ведущего из строя, в пределах контролируемого диапазона.

- Уменьшение потери данных из-за разделения мозга

Если у ведущего устройства есть разделение мозга и он теряет соединение с другими ведомыми устройствами, две вышеупомянутые конфигурации могут гарантировать, что, если он не может продолжать отправлять данные указанному количеству ведомых устройств, а ведомое устройство не отправляет себе подтверждающее сообщение в течение более 10 секунд, тогда запрос клиента на запись будет напрямую отклонен. Таким образом, в сценарии с разделенным мозгом теряется до 10 секунд данных.

## механизм преобразования sdown и odown

- sdown - это субъективное время простоя. Если Sentinel чувствует, что мастер не работает, то это субъективный простой.
- odown – объективное время простоя. Если кворум Sentinels чувствует, что мастер не работает, то это объективный простой.

Условия достижения снижения очень просты. Если Sentinel проверяет связь с мастером в течение времени, превышающего количество миллисекунд, указанное в `is-master-down-after-milliseconds`, мастер субъективно считается неработающим; если Sentinel получает кворум других Sentinel в течение указанного времени, а также считает, что мастер выключен, то он считается отключенным.

## Механизм автоматического обнаружения кластера Sentinel

Стражи обнаруживают друг друга через систему `pub/sub` Redis. Каждый Sentinel отправит сообщение на канал `__sentinel__:hello`. В это время все остальные Стражи могут усвоить это сообщение и почувствовать существование других Стражей.

Каждые две секунды каждый Sentinel отправляет сообщение на канал `__sentinel__:hello`, соответствующий одному из главных и ведомых устройств, которые он контролирует. Контент — это собственный хост, ip и рунид, а также конфигурация мониторинга этого мастера.

Каждый Sentinel также будет **мониторить** канал `__sentinel__:hello`, соответствующий каждому ведущему+ведомому устройству, за которым он следит, а затем обнаруживать существование других Sentinels, которые также контролируют этот главный+ведомый узел.

Каждый Sentinel также будет обмениваться конфигурациями мониторинга для `master` с другими Sentinel для синхронизации конфигураций мониторинга друг с другом.

## Автоматическое исправление конфигурации ведомого устройства

Sentinel будет отвечать за автоматическое исправление некоторых конфигураций ведомого устройства. Например, если ведомое устройство хочет стать потенциальным кандидатом на ведущего устройства, Sentinel гарантирует, что ведомое устройство скопирует данные существующего ведущего устройства; если ведомое устройство подключено к неправильному ведущему устройству, например, после аварийного переключения, Sentinel обеспечит подключение к правильному ведущему устройству.

## Алгоритм выбора подчиненного->ведущего

Если ведущий считается отключенным и большинство Sentinels разрешают переключение главный/подчиненный, то определенный Sentinel выполнит операцию переключения главный/подчиненный. В это время сначала должен быть избран раб, и будет рассмотрена некоторая информация о рабе:

- Время отключения от мастера
- подчиненный приоритет
- смещение копии
- идентификатор запуска

Если ведомое устройство было отключено от ведущего более 10 раз `down-after-milliseconds` плюс время, в течение которого ведущее устройство не работало, то ведомое устройство считается непригодным для избрания в качестве ведущего.

```
(down-after-milliseconds * 10) + milliseconds_since_master_is_in_SDOWN_state
```

Далее рабы будут отсортированы:

- Сортировка по приоритету подчиненного устройства. Чем ниже приоритет подчиненного устройства, тем выше приоритет.
— Если приоритеты слейвов одинаковы, то смотрите по смещению реплики, какой слейв скопировал больше данных, чем позже смещение, тем выше приоритет.
- Если два вышеуказанных условия одинаковы, выберите подчиненное устройство с меньшим идентификатором запуска.

## кворум и большинство

Каждый раз, когда Sentinel необходимо переключить между активным и резервным режимами, сначала нужно считать определенное количество Sentinel отключенными, а затем выбрать Sentinel для выполнения переключения. Этот Sentinel также должен быть авторизован большинством Sentinel, прежде чем он сможет официально выполнить переключение.

Если кворум < большинства, например, 5 Sentinels, большинство равно 3 и кворум установлен на 2, то только 3 Sentinels имеют право выполнять переключение.

Но если кворум >= большинства, то необходимо авторизовать определенное количество кворума Sentinels. Например, если имеется 5 Sentinels и кворум равен 5, то все 5 Sentinels должны согласиться на авторизацию, прежде чем можно будет выполнить переключение.

## эпоха конфигурации

Sentinel будет отслеживать набор главных и подчиненных устройств Redis и иметь соответствующие конфигурации мониторинга.

Sentinel, выполняющий переключение, получит эпоху конфигурации от нового ведущего устройства (salve->master), на которое будет переключено, что является номером версии. Номер версии каждого коммутатора должен быть уникальным.

Если первому выбранному Sentinel не удастся переключиться, остальные Sentinel будут ждать истечения времени ожидания переключения при сбое, а затем продолжат выполнять переключение. В это время новая эпоха конфигурации будет получена как новый номер версии.

## распространение конфигурации

После того, как Sentinel завершит переключение, он обновит и сгенерирует последнюю основную конфигурацию локально, а затем синхронизирует ее с другими Sentinels через механизм сообщений `pub/sub`, упомянутый ранее.

Номер предыдущей версии здесь очень важен, поскольку различные сообщения публикуются и отслеживаются через канал, поэтому после того, как Sentinel завершит новое переключение, новая основная конфигурация будет следовать за новым номером версии. Другие Sentinels обновляют свои основные конфигурации на основе номера версии.
