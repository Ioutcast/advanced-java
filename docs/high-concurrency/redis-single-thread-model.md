#Разница между Redis и Memcached

## Вопрос на собеседовании

В чем разница между Redis и Memcached? Какова потоковая модель Redis? Почему один поток Redis может поддерживать высокий уровень параллелизма?

## Что хочет знать интервьюер

Это самый основной вопрос при обращении к Redis. Одним из основных внутренних принципов и характеристик Redis является то, что Redis на самом деле представляет собой **однопоточную рабочую модель**. Если вы этого не знаете, то, когда вы позже будете играть с Redis, разве вы ничего не будете знать, если что-то пойдет не так?

Интервьюер также может спросить вас о разнице между Redis и Memcached, но Memcached был решением кэширования, обычно используемым крупными интернет-компаниями в первые годы, но теперь в последние годы это в основном Redis, и немногие компании используют Memcached.

## Анализ вопросов на собеседовании

### В чем разница между Redis и Memcached?

#### Redis поддерживает сложные структуры данных

По сравнению с Memcached, Redis имеет [Больше структур данных](./redis-data-types.md) и может поддерживать более широкие операции с данными. Если вам нужен кеш для поддержки более сложных структур и операций, Redis будет хорошим выбором.

#### Redis изначально поддерживает режим кластера

В Redis3.

#### Сравнение производительности

Поскольку Redis использует только одно ядро, а Memcached может использовать несколько ядер, Redis имеет более высокую производительность, чем Memcached, при хранении небольших данных в среднем на одно ядро. Для данных размером более 100 тыс. производительность Memcached выше, чем у Redis. Хотя Redis в последнее время оптимизирует производительность хранения больших данных, она все равно немного уступает Memcached.

### Потоковая модель Redis

Redis внутренне использует обработчик событий файла `file event handler`. Этот обработчик файловых событий является однопоточным, поэтому Redis называется однопоточной моделью. Он использует механизм мультиплексирования ввода-вывода для одновременного прослушивания нескольких сокетов и помещает сокет, генерирующий событие, в очередь памяти. Диспетчер событий выбирает соответствующий обработчик событий для обработки в зависимости от типа события в сокете.

Структура обработчика событий файла состоит из 4 частей:

- Несколько розеток
- Мультиплексор ввода-вывода
- Диспетчер файловых событий
- Процессор событий (процессор ответа на соединение, процессор запроса команды, процессор ответа команды)

Несколько сокетов могут одновременно генерировать разные операции, каждая из которых соответствует отдельному событию файла, но мультиплексор ввода-вывода будет прослушивать несколько сокетов и помещать сокеты, генерирующие события, в очередь. Диспетчер событий каждый раз извлекает из очереди один сокет и передает его соответствующему процессору событий для обработки в соответствии с типом события сокета.

Давайте посмотрим на процесс связи между клиентом и Redis:

![Redis-single-thread-model](./images/redis-single-thread-model.png)

Вы должны понимать, что связь осуществляется через сокеты. Студенты, которые ничего не понимают, могут сначала ознакомиться с программированием сетей сокетов.

Во-первых, когда процесс сервера Redis инициализируется, событие `AE_READABLE` сокета сервера будет связано с процессором ответа на соединение.

Клиентский сокет01 запрашивает сокет сервера процесса Redis для установления соединения. В это время сокет сервера сгенерирует событие `AE_READABLE`. После того как мультиплексор ввода-вывода прослушивает событие, сгенерированное сокетом сервера, он помещает сокет в очередь. Диспетчер файловых событий получает сокет из очереди и передает его **процессору ответа на соединение**. Обработчик ответа на соединение создаст сокет01, который сможет взаимодействовать с клиентом, и свяжет событие `AE_READABLE` сокета 01 с обработчиком запроса команды.

Предположим, что в это время клиент отправляет запрос `set key value`. В это время сокет01 в Redis сгенерирует событие `AE_READABLE`. Мультиплексор ввода-вывода помещает Socket01 в очередь. В это время диспетчер событий получает из очереди событие `AE_READABLE`, сгенерированное сокетом01. Из-за предыдущего `AE_READABLE` сокета01 событие было связано с обработчиком запроса команды, поэтому диспетчер событий передает событие обработчику запроса команды для обработки. Команда запрашивает процессор прочитать `key value` из сокета 01 и завершить настройку `key value` в своей памяти. Когда операция завершается, она связывает событие `AE_WRITABLE` сокета 01 с обработчиком ответа на команду.

Если клиент в это время готов получить возвращаемый результат, то сокет01 в Redis сгенерирует событие `AE_WRITABLE`, которое также будет помещено в очередь. Диспетчер событий находит соответствующий процессор ответа на команду, а процессор ответа на команду вводит результат этой операции в сокет 01, например `ok`, а затем освобождает связь между событием `AE_WRITABLE` сокета 01 и процессором ответа на команду.

На этом общение завершается. Что касается процесса коммуникации Redis, читателям рекомендуется прочитать «[Дизайн и реализация Redis — Хуан Цзяньхун](https://github.com/doocs/technical-books#database)» для систематического изучения.

### Почему однопоточная модель Redis настолько эффективна?

- Чистые операции с памятью.
- Ядро основано на неблокирующем механизме мультиплексирования ввода-вывода.
- Реализовано на языке C. Вообще говоря, программы, реализованные на языке C, «ближе» к операционной системе и выполняются относительно быстрее.
- Один поток позволяет избежать проблемы частого переключения контекста многопотоков и предотвращает возможные проблемы конкуренции, вызванные многопоточностью.

### Redis 6.0 начинает внедрять многопоточность

**Внимание! **В версиях после Redis 6.0 отказались от однопоточной модели. **Redis, который изначально работал с одним потоком, также начал выборочно использовать многопоточную модель**.

Раньше мы еще подчеркивали эффективность однопоточной модели Redis. Почему нам следует вводить многопоточность сейчас? Фактически это показывает, что Redis больше не имеет преимуществ в некоторых аспектах. Поскольку системные вызовы чтения и записи для чтения и записи по сети занимают большую часть процессорного времени во время выполнения Redis, если чтение и запись по сети сделать многопоточными, производительность будет значительно повышена.

**Многопоточная часть Redis используется только для обработки чтения и записи сетевых данных и анализа протоколов, а выполнение команд по-прежнему является однопоточным. ** Причина такой конструкции в том, что Redis не усложняется из-за многопоточности и требует контроля проблем параллелизма, таких как ключи, lua, транзакции, LPUSH/LPOP и т. д.

### Резюме

Redis предпочитает использовать однопоточную модель для обработки клиентских запросов главным образом потому, что ЦП не является узким местом сервера Redis, поэтому повышение производительности, обеспечиваемое использованием многопоточной модели, не может компенсировать затраты на разработку и обслуживание, которые она приносит. Узким местом производительности системы также являются операции сетевого ввода-вывода; а Redis вводит многопоточные операции также из соображений производительности. Для некоторых крупных операций удаления пары ключ-значение пространство памяти освобождается неблокируемо через многопоточность (операция освобождения не блокирует чтение и запись сетевого ввода-вывода, поскольку сетевой ввод-вывод (команды чтения, записи и выпуска не выполняются в одном и том же потоке), это также может сократить время блокировки основного потока Redis и повысить эффективность выполнения.
