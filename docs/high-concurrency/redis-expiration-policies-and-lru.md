# Политика срока действия Redis и алгоритм LRU

## Вопрос на собеседовании

Каковы стратегии истечения срока действия Redis? Каковы механизмы устранения памяти? Напишите от руки реализацию кода LRU?

## Что хочет знать интервьюер

Если вы даже не знаете этого вопроса и растеряны при первом появлении и не можете на него ответить, то, когда вы пишете код онлайн, вы считаете само собой разумеющимся, что данные, записанные в Redis, обязательно будут существовать. Кто будет нести ответственность за различные ошибки в системе, которые возникнут в дальнейшем?

Есть два распространенных вопроса:

— Почему данные, записанные в Redis, отсутствуют?

Некоторые студенты могут столкнуться с тем, что Redis в производственной среде часто теряет некоторые данные. Однажды написанное, через некоторое время оно может исчезнуть. О боже, одноклассник, если ты задаешь этот вопрос, значит, ты бесполезен с Redis. Redis — это кеш, вы рассматриваете его как хранилище, верно?

Что такое кэш? Используйте память в качестве кэша. Память безгранична? Память драгоценна и ограничена, а диски дешевы и в изобилии. Машина может иметь десятки гигабайт памяти, но может иметь и несколько терабайт места на жестком диске. Redis в основном основан на использовании памяти для выполнения высокопроизводительных операций чтения и записи с высоким уровнем параллелизма.

Итак, поскольку память ограничена, например, Redis может использовать только 10 ГБ, что вы будете делать, если запишете в нее 20 ГБ данных? Конечно, данные 10G будут удалены, а затем данные 10G сохранятся. Итак, какие данные следует удалить? Какие данные сохраняются? Конечно, нам следует избавиться от редко используемых данных и сохранить часто используемые данные.

- Данные явно просрочены, почему они все еще занимают память?

Это определяется политикой истечения срока действия Redis.

## Анализ вопросов на собеседовании

### Политика срока действия Redis

Стратегия истечения срока действия Redis: **обычное удаление + отложенное удаление**.

Так называемое **регулярное удаление** означает, что по умолчанию Redis случайным образом выбирает некоторые ключи со сроком действия, установленным каждые 100 мс, проверяет, истек ли срок их действия, и удаляет их, если срок их действия истекает.

Предположим, в Redis 100 000 ключей и установлен срок их действия. Если вы будете проверять 100 000 ключей каждые несколько сотен миллисекунд, то Redis по сути умрет, а загрузка процессора будет очень высокой, которая будет потребляться вашей проверкой ключей с истекшим сроком действия. Обратите внимание, что это не распространяется на все ключи со сроком действия каждые 100 мс. Это было бы катастрофой для производительности. Фактически, Redis случайным образом выбирает несколько ключей каждые 100 мс, чтобы проверить и удалить их.

Но проблема в том, что регулярное удаление может привести к тому, что многие ключи с истекшим сроком действия не будут удалены, когда придет время. Так что же нам делать? Поэтому его удалили лениво. Это означает, что когда вы получите ключ, Redis проверит, истек ли срок действия ключа, если для него установлено время истечения срока действия? Если срок его действия истечет, он будет удален в это время и вам ничего не будет возвращено.

> При получении ключа, если срок действия ключа истек, он будет удален и ничего не будет возвращено.

Но на самом деле это пока проблематично. Если при обычном удалении пропускается много ключей с истекшим сроком действия, а затем вы не проверяете их вовремя и не используете отложенное удаление, что произойдет в этот раз? Что делать, если в памяти накапливается большое количество ключей с истекшим сроком действия, что приводит к исчерпанию блока памяти Redis?

Ответ: **Используйте механизм исключения памяти**.

### Механизм устранения памяти

Механизмы устранения памяти Redis включают следующее:

- noeviction: если памяти недостаточно для размещения вновь записанных данных, новая операция записи сообщит об ошибке. Вообще этим никто не пользуется, это действительно отвратительно.
- **allkeys-lru**: если памяти недостаточно для размещения вновь записанных данных, в **пространстве ключей** удалите ключ, который использовался реже всего (это **наиболее часто используемый**).
- allkeys-random: когда памяти недостаточно для размещения вновь записанных данных, ключ случайным образом удаляется из **пространства ключей**. Обычно это не используется. Почему это должно быть случайно? Необходимо удалить ключ, который использовался реже всего.
- Летучий-lru: Когда памяти недостаточно для размещения вновь записанных данных, в пространстве ключей с установленным сроком действия удалите ключ, который использовался реже всего (это, как правило, не подходит).
- Нестабильно-случайный: когда памяти недостаточно для размещения вновь записанных данных, ключ будет случайным образом удален из пространства ключей с установленным сроком действия.
- voluty-ttl: когда памяти недостаточно для размещения вновь записанных данных, в пространстве ключей с установленным сроком действия сначала будут удалены ключи с более ранним сроком действия.

### Напишите алгоритм LRU от руки

LRU — это аббревиатура от Least Late Used, что переводится как «наименее недавно использованный». Другими словами, алгоритм LRU удалит кэш, который использовался реже всего, и передаст его последнему использованному кэшу. Чаще всего читаются те, которые читаются чаще всего, поэтому, эффективно используя алгоритм LRU, мы можем обеспечить эффективность кэширования данных горячих точек и улучшить использование памяти службой кэширования.

Так как же этого добиться?

На самом деле идея реализации очень проста, как на картинке ниже.

![](./images/lru.png)

Вы можете написать оригинальный алгоритм LRU прямо на месте, но объем кода слишком велик и кажется нереальным.

Вам не обязательно создавать свой собственный LRU снизу вверх вручную, но вы должны, по крайней мере, знать, как использовать существующие структуры данных JDK для реализации Java-версии LRU.

![](./images/lru-cache.png)

```java
public class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private int capacity;

    /**
     * 传递进来最多能缓存多少数据
     *
     * @param capacity 缓存大小
     */
    public LRUCache(int capacity) {
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }

    /**
     * 如果map中的数据量大于设定的最大容量，返回true，再新加入对象时删除最老的数据
     *
     * @param eldest 最老的数据项
     * @return true则移除最老的数据
     */
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        // 当 map中的数据量大于指定的缓存个数的时候，自动移除最老的数据
        return size() > capacity;
    }
}
```
