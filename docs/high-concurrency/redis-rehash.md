# Процесс перефразирования Redis

## Вопрос на собеседовании

Вы когда-нибудь понимали процесс перефразирования Redis?

## Что хочет знать интервьюер

Эта точка знаний представляет собой относительно низкочастотную точку собеседования в Redis, но когда вы представляете процесс перефразирования HashMap или процесс перефразирования ConcurrentHashMap, вы можете взять на себя инициативу и упомянуть интервьюеру, что вы не только понимаете их, но и понимаете процесс перефразирования в Redis.

Redis славится своей высокой скоростью и хорошей производительностью. Мы знаем, что возможности Redis вначале ограничены. Когда мощности недостаточно, ее необходимо расширить. Каков метод расширения? Будут ли данные перенесены все сразу? Когда объем данных достигнет десятков миллионов, это обязательно заблокирует выполнение команд Redis. Поэтому очень важно понимать процесс перефразирования в Redis.

## Анализ вопросов на собеседовании

Как мы все знаем, Redis в основном используется для хранения пар ключ-значение (`Key-Value Pair`), причем метод хранения пар ключ-значение реализуется словарем, а нижний уровень словаря в Redis реализуется через хеш-таблицу. Сохраняйте пары ключ-значение в словаре через узлы хеш-таблицы. Подобно HashMap в Java, ключ сопоставляется с положением узла хеш-таблицы с помощью хэш-функции.

Структура данных словаря в Redis следующая:

```c
// 字典对应的数据结构，有关hash表的结构可以参考redis源码，再次就不进行描述
typedef struct dict {
    dictType *type;  // 字典类型
    void *privdata;  // 私有数据
    dictht ht[2];    // 2个哈希表，这也是进行rehash的重要数据结构，从这也看出字典的底层通过哈希表进行实现。
    long rehashidx;   // rehash过程的重要标志，值为-1表示rehash未进行
    int iterators;   //  当前正在迭代的迭代器数
} dict;
```

При расширении или сжатии хеш-таблицы программе необходимо перехешировать все пары ключ-значение, содержащиеся в существующей хеш-таблице, в новую хеш-таблицу. Конкретный процесс заключается в следующем:

### 1. Выделите место для резервной хеш-таблицы словаря.

Если выполняется операция расширения, размер резервной хеш-таблицы составляет 2 дюйма (степень n 2) первой пары ключ-значение, которая больше или равна количеству пар ключ-значение хеш-таблицы, которую необходимо расширить*2; [`5*2=10,`Таким образом, емкость резервной хеш-таблицы равна первым 2 дюймам, которые больше 10, то есть 16]

Если выполняется операция сжатия, размер резервной хеш-таблицы составляет 2 дюйма от первого количества пар ключ-значение, которое больше или равно количеству пар ключ-значение (`ht[0] .used`) хеш-таблицы, которую необходимо расширить.

### 2. Прогрессивная перефразировка

Когда объем данных очень велик (десятки миллионов или миллиарды), процесс перехеширования не завершается сразу, а завершается постепенно. Преимущество **прогрессивного перехэширования** заключается в том, что он не влияет на сервер.

Суть прогрессивного перефразирования:

1. Благодаря rehasidx вычислительная работа, необходимая для повторного хеширования пар ключ-значение, равномерно распределяется между каждой операцией добавления, удаления, поиска и обновления в словаре, что позволяет избежать огромного объема вычислений, вызванного централизованным перехешированием.
2. В процессе перехэширования каждый раз, когда словарь добавляется, удаляется, выполняется поиск или обновляется, в дополнение к выполнению указанных операций программа также перехэширует все пары ключ-значение в индексе rehashidx исходной хеш-таблицы в резервную хэш-таблицу. Когда работа по перехэшированию будет завершена, программа увеличит значение атрибута rehashidx на 1.
