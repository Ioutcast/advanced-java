# Механизм сохранения Redis

## Вопрос на собеседовании

Каковы методы сохранения данных в Redis? Каковы преимущества и недостатки различных механизмов сохранения? Как реализован базовый механизм персистентности?

## Что хочет знать интервьюер

Если Redis кэширует данные только в памяти, если Redis выйдет из строя, а затем перезапустится, все данные в памяти будут потеряны. Вы должны использовать механизм сохранения Redis для записи данных в память и медленно и асинхронно записывать данные в файл на диске для сохранения.

Если Redis выйдет из строя и перезапустится, он может автоматически загрузить с диска некоторые ранее сохраненные данные. Небольшая часть данных может быть потеряна, но, по крайней мере, не все данные будут потеряны.

На самом деле это то же самое. Он нацелен на некоторые проблемы, с которыми можно столкнуться в производственной среде Redis. То есть, если Redis зависнет, а потом перезапустится, не потеряются ли все данные в памяти? Можно ли восстановить данные при перезагрузке?

## Анализ вопросов на собеседовании

Постоянство в основном используется для аварийного восстановления и восстановления данных. Его также можно отнести к каналу высокой доступности. Например, если ваш Redis полностью отключен, Redis станет недоступен. Что вам нужно сделать, так это сделать Redis доступным как можно скорее.

Перезапустите Redis и позвольте ему предоставлять внешние службы как можно скорее. Если резервное копирование данных не выполнено, Redis не будет доступен после запуска в это время, и данные исчезнут.

Очень вероятно, что при поступлении большого количества запросов кеш не сможет поразить, а данные вообще не удастся найти в Redis. В настоящее время он не работает, и возникает проблема **лавины кэша**. Если Redis не обрабатывает все запросы, они перейдут к источнику данных, например базе данных mysql. Внезапно MySQL берет на себя высокий уровень параллелизма, а затем зависает...

Если вы хорошо справляетесь с сохранением Redis и реализуете план резервного копирования и восстановления на уровне предприятия, то даже если ваш Redis выйдет из строя, вы сможете быстро восстановить его путем резервного копирования данных и предоставлять услуги внешнему миру, как только он будет восстановлен.

### Два способа сохранения Redis

- RDB: механизм сохранения RDB выполняет **периодическое** сохранение данных в Redis.
- AOF: механизм AOF записывает каждую команду записи в журнал и записывает ее в файл журнала в режиме `append-only`. При перезапуске Redis весь набор данных можно восстановить путем **воспроизведения** инструкций записи в журнале AOF.

Через RDB или AOF данные из памяти Redis можно сохранить на диск, а затем создать резервную копию данных в других местах, например в Alibaba Cloud и других облачных сервисах.

Если Redis выйдет из строя и данные в памяти и на диске сервера будут утеряны, вы можете скопировать предыдущие данные обратно из облачного сервиса, поместить их в указанный каталог, а затем перезапустить Redis. Redis автоматически восстановит данные в памяти на основе данных в постоянном файле данных и продолжит предоставлять услуги внешнему миру.

Если используются механизмы сохранения как RDB, так и AOF, **AOF** будет использоваться для восстановления данных при перезапуске Redis, поскольку **данные в AOF** являются более полными**.

#### Преимущества и недостатки RDB

- RDB создаст несколько файлов данных, каждый из которых представляет данные Redis в определенный момент. Этот метод использования нескольких файлов данных очень подходит для холодного резервного копирования. Этот полный файл данных можно отправить в какое-нибудь удаленное безопасное хранилище, например в облачный сервис Amazon S3. В Китае это может быть распределенное хранилище ODPS Alibaba Cloud. Данные в Redis регулярно резервируются с использованием заранее определенной стратегии резервного копирования.
- RDB оказывает очень незначительное влияние на внешние службы чтения и записи, предоставляемые Redis, что позволяет Redis поддерживать высокую производительность, поскольку основному процессу Redis нужно только разветвить дочерний процесс и позволить дочернему процессу выполнять дисковые операции ввода-вывода для сохранения RDB.
— По сравнению с механизмом сохранения AOF, перезапуск и восстановление процесса Redis происходит быстрее непосредственно на основе файла данных RDB.
— Если вы хотите потерять как можно меньше данных при сбое Redis, то RDB не так хорош, как AOF. Вообще говоря, файлы моментальных снимков данных RDB создаются каждые 5 минут или чаще. На данный момент вы должны принять тот факт, что в случае сбоя процесса Redis данные за последние 5 минут (или даже дольше) будут потеряны.
- Каждый раз, когда RDB разветвляет дочерний процесс для создания файла данных моментального снимка RDB, если файл данных особенно велик, это может привести к приостановке службы, предоставляемой клиентом, на несколько миллисекунд или даже секунд.

#### Преимущества и недостатки АОФ

- AOF может лучше защитить данные от потери. Как правило, AOF выполняет операцию `fsync` через фоновый поток каждые 1 секунду, при этом теряется максимум 1 секунда данных.
- Файлы журналов AOF записываются в режиме `append-only`, поэтому накладные расходы на адресацию диска отсутствуют, производительность записи очень высока, и файл нелегко повредить. Даже если хвостик файла поврежден, его легко починить.
— Даже если файл журнала AOF слишком велик, операции фоновой перезаписи не повлияют на чтение и запись клиента. Потому что при регистрации `rewrite` инструкции будут сжаты для создания минимального журнала, необходимого для восстановления данных. При создании нового файла журнала старый файл журнала по-прежнему записывается как обычно. Когда новый объединенный файл журнала будет готов, просто поменяйте местами старый и новый файлы журнала.
- Команды файла журнала AOF записываются в удобной для чтения форме. Эта функция очень подходит для экстренного восстановления после катастрофического случайного удаления. Например, если кто-то случайно очистит все данные с помощью команды `flushall`, если в это время не произошел фоновый `rewrite`, файл AOF можно скопировать немедленно, последняя команда `flushall` будет удалена, а затем файл `AOF` будет возвращен, и все данные могут быть автоматически восстановлены с помощью механизма восстановления.
- Для одного и того же фрагмента данных файлы журнала AOF обычно больше, чем файлы моментальных снимков данных RDB.
- После включения AOF поддерживаемое количество операций записи в секунду будет ниже, чем количество операций записи в секунду, поддерживаемое RDB, поскольку AOF обычно настроен на регистрацию файлов один раз в секунду `fsync`. Конечно, раз в секунду `fsync` производительность по-прежнему очень высока. (Если запись выполняется в реальном времени, количество запросов в секунду значительно снизится, а производительность Redis значительно снизится)
- В AOF ранее уже возникала ошибка. Когда данные были восстановлены через журналы, записанные AOF, те же самые данные не были восстановлены. Таким образом, более сложный метод воспроизведения журнала команд `merge`, такой как AOF, более хрупкий и подвержен ошибкам, чем метод на основе RDB, позволяющий каждый раз сохранять полный файл моментального снимка данных. Однако AOF призван избежать ошибок, вызванных процессом перезаписи. Таким образом, каждая перезапись не объединяется на основе старого журнала инструкций, а восстанавливается на основе данных, находящихся в памяти в тот момент. Таким образом, устойчивость будет намного выше.

### Как выбрать между RDB и AOF?

- Не используйте просто RDB, так как это приведет к потере большого количества данных;
— Не используйте просто AOF, потому что есть две проблемы: во-первых, вы используете AOF в качестве холодного резервного копирования, а скорость восстановления выше без RDB в качестве холодного резервного копирования; во-вторых, RDB каждый раз просто и грубо генерирует снимки данных, что более надежно и позволяет избежать ошибок сложных механизмов резервного копирования и восстановления, таких как AOF;
— Redis поддерживает одновременное включение двух методов сохранения. Мы можем использовать два механизма сохранения данных AOF и RDB в сочетании, используя AOF, чтобы гарантировать, что данные не будут потеряны, в качестве первого выбора для восстановления данных; используйте RDB для выполнения холодного резервного копирования различной степени. Если файлы AOF потеряны или повреждены и недоступны, вы также можете использовать RDB для быстрого восстановления данных.
