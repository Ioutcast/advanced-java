# Принцип распределенной архитектуры ES

## Вопрос на собеседовании

Можете ли вы объяснить принцип распределенной архитектуры ES (как ES обеспечивает распространение)?

## Что хочет знать интервьюер

С точки зрения поиска Lucene — самая популярная поисковая библиотека. Несколько лет назад люди в отрасли обычно спрашивали: знаете ли вы Lucene? Знаете ли вы принцип инвертированного индекса? Его уже давно нет, потому что многие проекты сейчас напрямую используют распределенную поисковую систему на основе Lucene — ElasticSearch, называемую ES.

Сейчас распределенный поиск по сути стал стандартной конфигурацией Java-систем в большинстве интернет-отраслей, среди которых особой популярностью пользуется ES. Когда несколько лет назад ES не был популярен, все обычно использовали Solr. Но в последние два года большинство компаний и проектов начали обращаться к ES.

Поэтому в интернет-интервью с вами обязательно будут говорить о распределенных поисковых системах, и обязательно будут говорить о ES. Если вы действительно не знаете, то вы действительно не в курсе.

Если интервьюер задает вам первый вопрос, он обычно задает его вам. Можете ли вы представить проект распределенной архитектуры ES? Просто взгляните на свое базовое понимание архитектуры распределенной поисковой системы.

## Анализ вопросов на собеседовании

Концепция дизайна ElasticSearch — это распределенная поисковая система, нижний уровень которой фактически основан на lucene. Основная идея состоит в том, чтобы запустить несколько экземпляров процесса ES на нескольких машинах для формирования кластера ES.

Основной единицей хранения данных в ES является индекс. Например, если вы хотите сохранить некоторые данные заказа в ES, вам следует создать индекс `order_idx` в ES. Все данные заказа будут записаны в этот индекс. Индекс почти эквивалентен базе данных в MySQL.

```
index -> type -> mapping -> document -> field
```

Что ж, чтобы сделать введение более простым, позвольте мне провести аналогию. Но помните, не рисуйте знак равенства, аналогия предназначена только для простоты понимания.

индекс эквивалентен базе данных MySQL. Тип нельзя сравнивать с MySQL. В индексе может быть несколько типов. Поля каждого типа похожи, но есть некоторые небольшие различия. Предположим, что существует индекс, который является индексом заказа и конкретно содержит данные заказа. Как и при создании таблицы в MySQL, некоторые заказы относятся к физическим товарам, таким как предмет одежды или пара обуви; некоторые заказы предназначены для виртуальных товаров, таких как игровые очки и пополнение счета телефона. Большинство полей двух заказов одинаковы, но некоторые поля могут иметь небольшие различия.

Таким образом, в индексе заказов будут созданы два типа: один — тип заказа на физические товары, а другой — тип заказа на виртуальные товары. Большинство полей этих двух типов одинаковы, но некоторые поля различаются.

Во многих случаях в индексе может быть только один тип, но если в индексе есть несколько типов (**Примечание**, `mapping types` Эта концепция была полностью удалена в ElasticSearch 7. Каждый тип имеет сопоставление. Если вы думаете, что тип представляет собой определенную таблицу, индекс представляет собой тип, которому принадлежат несколько типов, а сопоставление — это **определение структуры таблицы** этого типа. Когда вы создаете таблицу в MySQL, вы должны определить структуру таблицы, какие поля в ней находятся и какого типа. Фактически, часть данных, которые вы записываете в тип индекса, называется документом. Документ представляет собой строку в таблице в MySQL. Каждый документ имеет несколько полей, и каждое поле представляет значение поля в документе.

![es-index-type-mapping-document-field](./images/es-index-type-mapping-document-field.png)

Вы создаете индекс. Этот индекс можно разделить на несколько `shard`, и каждый шард хранит часть данных. Разделение нескольких осколков имеет свои преимущества. Во-первых, он поддерживает горизонтальное расширение. Например, если объем ваших данных составляет 3 ТБ и 3 сегмента, каждый сегмент содержит 1 ТБ данных. Если объем данных увеличится до 4Т, то, как его расширить, очень просто. Перестройте индекс с 4 сегментами и импортируйте данные. Во-вторых, это повышает производительность. Данные распределяются по нескольким шардам. Шардирование означает, что все операции на нескольких серверах будут выполняться параллельно и распределяться по нескольким машинам, что повышает пропускную способность и производительность.

Следующее, что данные этого шарда на самом деле имеют несколько резервных копий. То есть у каждого шарда есть один `primary shard`, отвечающий за запись данных, но есть и несколько `replica shard`. После того, как `primary shard` запишет данные, они будут синхронизированы с несколькими другими `replica shard`.

![es-cluster](./images/es-cluster.png)

Благодаря этому решению реплики данные каждого сегмента имеют несколько резервных копий. Если какая-то машина выйдет из строя, это не имеет значения. На других машинах есть другие копии данных. Высокая доступность.

Если кластер ES имеет несколько узлов, один узел будет автоматически выбран в качестве главного узла. Этот главный узел фактически выполняет некоторую работу по управлению, например, поддерживает метаданные индекса и переключает идентификаторы основного сегмента и сегмента-реплики. Если главный узел выйдет из строя, в качестве главного узла будет выбран новый узел.

Если неглавный узел выйдет из строя, главный узел передаст идентификатор основного сегмента на выключенном узле сегменту-реплике на других машинах. Тогда, если вы отремонтируете сбитую машину и перезагрузите ее, мастер-нода будет контролировать распределение недостающего шарда реплики, синхронизировать последующие измененные данные и т. д., чтобы кластер вернулся в нормальное состояние.

Проще говоря, если не главный узел выходит из строя. Тогда основной шард на этом узле исчезнет. Ну а мастер переключит шард-реплику (на других машинах), соответствующий основному шарду, на основной шард. Если сбитую машину отремонтировать, отремонтированный узел уже не является основным шардом, а является репликой.

Фактически, вышеизложенное представляет собой самый базовый архитектурный проект ElasticSearch как распределенной поисковой системы.
