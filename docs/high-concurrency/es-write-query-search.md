## Анализ вопросов на собеседовании

### es процесс записи данных

- Клиент выбирает узел для отправки запроса. Этот узел — `coordinating node` (координирующий узел).
- `coordinating node` Маршрутизирует документ и пересылает запрос соответствующему узлу (с основным сегментом).
- `primary shard` на реальном узле обрабатывает запрос, а затем синхронизирует данные с `replica node`.
- `coordinating node` Если `primary node` и все `replica node` найдены, результат ответа будет возвращен клиенту.

![es-write](./images/es-write.png)

###es процесс чтения данных

Вы можете запросить его через `doc id`. Он будет хэшироваться на основе `doc id`, чтобы определить, какой сегмент `doc id` был выделен в тот момент, и запросить его из этого сегмента.

- Клиент отправляет запрос **любому** узлу, становясь `coordinate node`.
- `coordinate node` выполняет хеш-маршрутизацию на `doc id` и перенаправляет запрос на соответствующий узел. В это время `round-robin` **алгоритм случайного опроса** будет использоваться для случайного выбора одного из `primary shard` и всех его реплик для балансировки нагрузки запросов на чтение.
- Узел, получивший запрос, возвращает документ на `coordinate node`.
- `coordinate node` Возврат документа клиенту.

### es Процесс поиска данных

Самая мощная вещь в es — это полнотекстовый поиск. Например, если у вас есть три части данных:

```
java真好玩儿啊
java好难学啊
j2ee特别牛
```

Если вы выполните поиск по ключевому слову `java`, вы найдете `document`, содержащий `java`. es вернется к вам: Java — это так весело, но Java так сложно выучить.

- Клиент отправляет запрос на `coordinate node`.
- Координационный узел пересылает поисковый запрос на `primary shard` или `replica shard`, соответствующий **всем** сегментам, в зависимости от того, что подходит.
- Фаза запроса: каждый сегмент возвращает свои собственные результаты поиска (фактически некоторые `doc id` ) на координационный узел, который выполняет объединение данных, сортировку, разбиение по страницам и другие операции для получения окончательных результатов.
- Фаза выборки: затем координирующий узел извлекает фактические данные `document` из каждого узла на основе `doc id` и, наконец, возвращает их клиенту.

> Запросы на запись записываются в основной сегмент, а затем синхронизируются со всеми сегментами реплик; Запросы на чтение могут быть прочитаны из основного сегмента или сегмента-реплики с использованием алгоритма случайного опроса.

### Основной принцип записи данных

![es-write-detail](./images/es-write-detail.png)

Сначала запишите в буфер памяти, поиск данных в буфере невозможен; в то же время данные записываются в файл журнала транслога.

Если буфер почти заполнен или по истечении определенного периода времени, данные буфера памяти `refresh` будут перемещены в новый `segment file`. Однако в это время данные не поступают непосредственно в файл диска `segment file`, а сначала поступают в `os cache`. Это процесс `refresh`.

Каждую секунду es записывает данные в буфер в **новый** `segment file`, и каждую секунду генерируется **новый дисковый файл** `segment file`. Этот `segment file` хранит данные, записанные в буфер за последнюю 1 секунду.

Но если в это время в буфере данных нет, то операция обновления, естественно, не будет выполнена. Если в буфере есть данные, операция обновления по умолчанию будет выполняться раз в секунду, и новый файл сегмента будет сброшен.

В операционной системе файлы на диске на самом деле имеют нечто под названием `os cache`, которое является кэшем операционной системы. То есть, прежде чем данные будут записаны в файл на диске, они сначала войдут в `os cache`, который представляет собой кеш-память на уровне операционной системы. Пока данные из `buffer` сбрасываются в `os cache` в результате операции обновления, по этим данным можно осуществлять поиск.

Почему это называется **квази-реальным временем**? `NRT`, полное имя `near real-time`. По умолчанию обновление происходит каждые 1 секунду, поэтому es работает в квазиреальном времени, поскольку записанные данные можно увидеть только через 1 секунду. Вы можете использовать `restful api` или `java api` ES для **ручного** выполнения операции обновления, которая заключается в ручном обновлении данных в буфере в `os cache`, чтобы можно было немедленно выполнить поиск данных. Пока данные вводятся в `os cache`, буфер будет очищен, поскольку нет необходимости сохранять буфер, и данные сохраняются на диске в транслоге.

Повторите вышеуказанные шаги, новые данные продолжают поступать в буфер и транслогироваться, а данные `buffer` непрерывно записываются в новый `segment file` один за другим. Каждый раз, когда `refresh` завершается, буфер очищается, а транслог сохраняется. По мере продвижения этого процесса транслог будет становиться все больше и больше. Когда транслог достигнет определенной длины, будет запущена операция `commit`.

Первым шагом в операции фиксации является перемещение существующих данных `refresh` в буфере в `os cache` и очистка буфера. Затем запишите `commit point` в файл на диске, который идентифицирует все `segment file`, соответствующие этому `commit point`, и в то же время принудительно перенесите все данные, находящиеся в данный момент в `os cache`, в `fsync` в файл на диске. Наконец, **очистите** существующий файл журнала транслога, перезапустите транслог, и операция фиксации будет завершена.

Эта операция фиксации называется `flush`. По умолчанию `flush` автоматически выполняется раз в 30 минут, но если транслог слишком велик, `flush` также будет запущен. Операция сброса соответствует всему процессу фиксации. Мы можем вручную выполнить операцию очистки через es api и вручную синхронизировать данные из кэша ОС на диск.

Какова цель файла журнала транслога? Прежде чем выполнить операцию фиксации, данные остаются либо в буфере, либо в кэше операционной системы. И буфер, и кеш операционной системы являются памятью. Как только машина выйдет из строя, все данные в памяти будут потеряны. Поэтому операции, соответствующие данным, необходимо записывать в специальный файл журнала `translog`. Как только машина выйдет из строя и снова перезапустится, es автоматически прочитает данные в файле журнала транслога и восстановит их в буфер памяти и кеш операционной системы.

Translog фактически сначала записывается в кеш операционной системы. По умолчанию он сбрасывается на диск каждые 5 секунд. Поэтому по умолчанию 5 секунд данных могут оставаться только в кэше операционной системы буфера или файла транслога. Если в это время компьютер зависнет, 5 секунд данных будут потеряны. Однако при этом производительность выше, и теряется до 5 секунд данных. Вы также можете настроить транслог так, чтобы каждая операция записи выполнялась напрямую `fsync` на диск, но производительность будет намного хуже.

- `index.translog.sync_interval` Контролируйте, сколько времени потребуется транслогу для синхронизации с диском, минимум — 100 мс;
- `index.translog.durability` Обновляется ли транслог каждые 5 секунд или fsync для каждого запроса. Этот параметр имеет 2 значения: запрос (выполнять fsync при каждом запросе, es будет ждать, пока транслог fsync будет отправлен на диск, прежде чем вернуть успешный результат) и async (значение по умолчанию, транслог fsync выполняется каждые 5 секунд).

На самом деле, вы здесь. Если интервьюер не спрашивает вас о потере данных, вы можете похвастаться перед интервьюером здесь. Вы сказали, что на самом деле es сначала работает в квазиреальном времени, и данные можно искать после 1 секунды записи; данные могут быть потеряны. Данные в течение 5 секунд остаются в буфере, транслоговом кэше операционной системы, сегментном файловом кэше операционной системы, а не на диске. Если в это время компьютер выйдет из строя, произойдет **потеря данных** на 5 секунд.

**Подводя итог**, данные сначала записываются в буфер памяти, а затем обновляются в кэше операционной системы каждые 1 с. Данные можно искать, когда они достигают кэша операционной системы (поэтому мы говорим, что существует задержка в 1 с от записи до возможности поиска в es). Каждые 5 с данные записываются в файл транслога (поэтому, если машина выйдет из строя и все данные памяти будут потеряны, до 5 с данных будет потеряно). Когда транслог достаточно велик (или каждые 30 минут по умолчанию), будет запускаться операция фиксации для сброса всех данных в буфере в файл сегмента диска.

> После записи данных в файл сегмента одновременно устанавливается инвертированный индекс.

### Основной принцип удаления/обновления данных

Если это операция удаления, во время фиксации будет создан файл `.del`, который идентифицирует определенный документ как статус `deleted`. Тогда при поиске вы узнаете, был ли удален документ на основе файла `.del`.

Если это операция обновления, исходный документ помечается как статус `deleted`, а затем записывается новый фрагмент данных.

Каждый раз, когда буфер обновляется, будет генерироваться `segment file`, поэтому по умолчанию это один `segment file` каждую 1 секунду. Таким образом, `segment file` будет все больше и больше, и слияние будет выполняться регулярно. Во время каждого слияния несколько `segment file` будут объединены в один. В то же время документ с меткой `deleted` будет физически удален, а затем на диск будет записан новый `segment file`. Здесь будет записано `commit point`, чтобы идентифицировать все новые `segment file`, а затем открыть `segment file` Доступно для поиска, а старый `segment file` удалить.

### Основа люцена

Проще говоря, Lucene — это jar-пакет, содержащий различные инкапсулированные коды алгоритмов для создания инвертированных индексов. Когда мы разрабатываем на Java, нам просто нужно представить lucene jar, а затем разрабатывать на основе lucene API.

С помощью Lucene мы можем индексировать существующие данные, и Lucene организует для нас структуру индексных данных на локальном диске.

### Инвертированный индекс

В поисковых системах каждый документ имеет соответствующий идентификатор документа, а содержимое документа представлено в виде набора ключевых слов. Например, документ 1 сегментируется и извлекается 20 ключевых слов. Для каждого ключевого слова будет записан номер и место его появления в документе.

Затем инвертированный индекс представляет собой сопоставление ключевых слов с идентификаторами документов. Каждое ключевое слово соответствует серии файлов, и ключевые слова появляются в этих файлах.

Дай мне каштан.

Имеются следующие документы:

| Идентификатор документа | Док |
| ----- | ---------------------------------------------- |
| 1 | Отец Google Maps покидает Facebook |
| 2 | Отец Google Maps присоединяется к Facebook |
| 3 | Основатель Google Maps Расс покинул Google и присоединился к Facebook |
| 4 | Отец Google Maps покидает Facebook и связан с отменой проекта Wave |
| 5 | Расс, создатель Google Maps, присоединяется к социальной сети Facebook |

После сегментации документа получается следующий **инвертированный индекс**.

| WordID | Слово | Документы |
| ------ | -------- | ------------- |
| 1 | Гугл | 1, 2, 3, 4, 5 |
| 2 | Карта | 1, 2, 3, 4, 5 |
| 3 | Отец | 1, 2, 4, 5 |
| 4 | Смена работы | 1, 4 |
| 5 | Фейсбук | 1, 2, 3, 4, 5 |
| 6 | Присоединяйтесь | 2, 3, 5 |
| 7 | Основатель | 3 |
| 8 | Ларс | 3, 5 |
| 9 | уйти | 3 |
| 10 | против | 4 |
| .. | .. | .. |

Кроме того, практический инвертированный индекс также может записывать дополнительную информацию, например информацию о частоте документов, указывающую, сколько документов в коллекции документов содержат определенное слово.

Что ж, с помощью инвертированного индекса поисковые системы могут легко реагировать на запросы пользователей. Например, пользователь вводит запрос `Facebook`, а поисковая система ищет по инвертированному индексу и считывает документы, содержащие это слово. Эти документы представляют собой результаты поиска, предоставляемые пользователю.

Об инвертированных индексах следует отметить две важные детали:

- Все термины в инвертированном индексе соответствуют одному или нескольким документам;
- Термины в инвертированном индексе отсортированы в возрастающем лексикографическом порядке**

> Вышеупомянутое представляет собой простой каштан и не расположено строго в порядке возрастания словаря.
