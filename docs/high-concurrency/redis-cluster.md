Можете ли вы объяснить, как работает режим кластера Redis? Как адресуется ключ Redis в режиме кластера? Каковы алгоритмы распределенной адресации? Знаете ли вы алгоритм последовательного хеширования?

## Что хочет знать интервьюер

В последние несколько лет, если Redis хотел иметь несколько узлов и каждый узел хранил часть данных, это приходилось реализовывать с помощью некоторого промежуточного программного обеспечения, такого как `codis` или `twemproxy`. Существует некоторое промежуточное программное обеспечение Redis, вы читаете и пишете промежуточное программное обеспечение Redis, промежуточное программное обеспечение Redis отвечает за распределенное хранение ваших данных в экземплярах Redis на нескольких машинах.

За последние два года Redis продолжал развиваться, и Redis также продолжал выпускать новые версии. Текущий режим кластера Redis позволяет развертывать несколько экземпляров Redis на нескольких компьютерах. Каждый экземпляр хранит часть данных. В то же время каждый главный экземпляр Redis может быть связан с подчиненным экземпляром Redis, что автоматически гарантирует, что в случае зависания главного экземпляра Redis он автоматически переключится на подчиненный экземпляр Redis.

В настоящее время в новой версии Redis все используют кластер Redis, который представляет собой режим кластера Redis, который Redis изначально поддерживает, поэтому интервьюер обязательно даст вам несколько попыток поработать с кластером Redis. Если вы никогда не использовали кластер Redis, это нормально. В прошлом многие люди использовали такие клиенты, как codis, для поддержки кластеров, но вам, по крайней мере, придется изучить кластер Redis.

Если объем ваших данных небольшой, он в основном используется для реализации сценариев с высоким уровнем параллелизма и высокой производительности. Например, ваш кэш обычно составляет всего несколько G, и достаточно одной машины. Вы можете использовать репликацию, одного ведущего и нескольких ведомых. Количество подчиненных устройств зависит от необходимой вам пропускной способности чтения, а затем самостоятельно создайте дозорный кластер, чтобы обеспечить высокую доступность архитектуры Redis «главный-подчиненный».

Кластер Redis в основном ориентирован на сценарий **большие объемы данных+высокий уровень параллелизма+высокая доступность**. Кластер Redis поддерживает N главных узлов Redis, и каждый главный узел может монтировать несколько подчиненных узлов. Таким образом, весь Redis можно расширить по горизонтали. Если вы хотите поддерживать больший кэш данных, горизонтально разверните больше главных узлов, чтобы каждый главный узел мог хранить больше данных.

## Анализ вопросов на собеседовании

### Введение в кластер Redis

- Автоматически сегментировать данные и помещать часть данных на каждый мастер
- Обеспечивает встроенную поддержку высокой доступности, поэтому вы можете продолжать работу, когда некоторые мастера недоступны.

В кластерной архитектуре Redis каждый Redis должен открыть два номера портов, например, один — 6379, а другой — номер порта плюс 1w, например 16379.

Номер порта 16379 используется для связи между узлами, то есть связи по шине кластера, и используется для обнаружения неисправностей, обновления конфигурации и авторизации аварийного переключения. Шина кластера использует другой двоичный протокол, протокол `gossip`, для эффективного обмена данными между узлами, занимая меньшую пропускную способность сети и время обработки.

### Механизм внутренней связи между узлами

#### Основные принципы общения

Существует два способа поддержки метаданных кластера: централизованный и протокол сплетен. Узлы кластера Redis используют протокол сплетен для связи.

**Централизованный** — централизованное хранение метаданных кластера (информация об узлах, неисправностях и т. д.) на определенном узле. Типичным представителем централизованного хранилища метаданных является `storm` в сфере больших данных. Это распределенная вычислительная машина для больших данных в реальном времени и централизованная структура хранения метаданных. Нижний уровень основан на Zookeeper (промежуточном программном обеспечении распределенной координации) для хранения и обслуживания всех метаданных.

![zookeeper-centralized-storage](./images/zookeeper-centralized-storage.png)

Redis использует другой метод для поддержки метаданных кластера — протокол `gossip`. Все узлы содержат копию метаданных. Если изменения метаданных происходят на разных узлах, метаданные будут непрерывно отправляться на другие узлы, что позволяет другим узлам также изменять метаданные.

![Redis-gossip](./images/redis-gossip.png)

**Преимущества** **централизации** заключаются в том, что чтение и обновление метаданных происходит очень своевременно. Как только метаданные изменяются, они немедленно обновляются в централизованном хранилище, и другие узлы могут обнаружить это при чтении. **Недостаток** заключается в том, что необходимость обновления всех метаданных сосредоточена в одном месте, что может вызвать нагрузку на хранилище метаданных.

Преимущество слухов в том, что обновления метаданных относительно рассредоточены, а не сосредоточены в одном месте. Запросы на обновление будут отправляться всем узлам один за другим для обновления, что снижает нагрузку. Недостаток — обновления метаданных задерживаются, что может привести к отставанию некоторых операций в кластере.

- Порт 10000: у каждого узла есть порт, специально используемый для связи между узлами, который представляет собой номер порта, который предоставляет услуги + 10000, например 7001, тогда порт 17001 используется для связи между узлами. Каждый узел будет отправлять сообщения `ping` нескольким другим узлам через равные промежутки времени, и в то же время несколько других узлов будут возвращать `pong` после получения `ping`.

- Информация, которой обмениваются: информация включает информацию о сбоях, добавлении и удалении узла, информацию о хеш-слоте и т. д.

#### протокол сплетен

Протокол сплетен содержит множество сообщений, включая `ping`, `pong`, `meet`, `fail` и так далее.

— meet: узел отправляет сообщение meet вновь добавленному узлу, чтобы позволить новому узлу присоединиться к кластеру, а затем новый узел начнет взаимодействовать с другими узлами.

```bash
Redis-trib.rb add-node
```

Фактически, внутренне сообщение о сплетнях отправляется вновь добавленному узлу, чтобы уведомить этот узел о присоединении к нашему кластеру.

- Пинг: каждый узел будет часто отправлять пинги другим узлам, включая собственный статус и метаданные кластера, поддерживаемые им самим, а также обмениваться метаданными друг с другом посредством пингов.
- pong: Возвращает ping and meet, включая собственный статус и другую информацию, а также используется для трансляции информации и обновлений.
- сбой: после того, как узел определяет, что другой узел вышел из строя, он отправляет сообщение об ошибке другим узлам, чтобы уведомить другие узлы о том, что определенный узел не работает.

#### глубина сообщения ping

Некоторые метаданные необходимо передавать при проверке связи. Если это происходит часто, это может увеличить нагрузку на сеть.

Каждый узел будет выполнять 10 пингов в секунду и каждый раз выбирать 5 других узлов, с которыми не было связи в течение самого длительного времени. Конечно, если будет обнаружено, что задержка связи определенного узла достигает `cluster_node_timeout / 2`, немедленно отправьте пинг, чтобы избежать слишком длительной задержки обмена данными и слишком долгой задержки. Например, если в течение 10 минут не будет обмена данными между двумя узлами, то весь кластер окажется в серьезной ситуации несогласованности метаданных, что вызовет проблемы. Итак, `cluster_node_timeout` можно отрегулировать. Если его отрегулировать больше, это уменьшит частоту пинга.

Каждый раз, когда вы пингуете, вы приносите информацию о своем собственном узле и информацию 1/10 других узлов и отправляете их на обмен. Содержит информацию как минимум о `3` других узлах и не более `总节点数减 2` других узлах.

### Алгоритм распределенной адресации

- алгоритм хеширования (массовая перестройка кеша)
- Согласованный алгоритм хеширования (автоматическая миграция кэша) + виртуальный узел (автоматическая балансировка нагрузки)
- Алгоритм хэш-слота кластера Redis

#### алгоритм хеширования

Когда приходит ключ, сначала вычисляем значение хеш-функции, а затем берем по модулю количество узлов. Затем нажмите на разные главные узлы. После выхода из строя главного узла все запросы будут модулироваться на основе последнего количества оставшихся главных узлов и пытаться получить данные. Это приведет к тому, что **большинство запросов будет поступать, и все они не смогут получить эффективный кэш**, что приведет к попаданию большого объема трафика в базу данных.

![hash](./images/hash.png)

#### Согласованный алгоритм хеширования

Алгоритм согласованного хеширования организует все пространство значений хеш-функции в виртуальное кольцо. Все пространство организовано по часовой стрелке. На следующем этапе каждый главный узел (с использованием IP-адреса или имени хоста сервера) хешируется. Это определяет положение каждого узла в его хэш-кольце.

Когда приходит ключ, сначала вычисляем значение хеш-функции и определяем положение этих данных на кольце. Из этого положения «пройдите» по часовой стрелке вдоль кольца, первый встреченный мастер-узел — это место расположения ключа.

В алгоритме последовательного хеширования, если узел выходит из строя, затронутыми данными являются только данные между этим узлом и предыдущим узлом в кольцевом пространстве (первый узел, встреченный при движении против часовой стрелки), а другие данные не будут затронуты. То же самое касается добавления узла.

Рангоу, когда в алгоритме последовательного хеширования слишком мало узлов, легко вызвать проблемы с **горячими точками кэша** из-за неравномерного распределения узлов. Чтобы решить эту проблему с горячими точками, алгоритм согласованного хеширования вводит механизм виртуального узла, то есть для каждого узла вычисляется несколько хешей, и виртуальный узел размещается в каждой позиции результата расчета. Это обеспечивает равномерное распределение данных и балансировку нагрузки.

![consistent-hashing-algorithm](./images/consistent-hashing-algorithm.png)

#### Алгоритм хэш-слота кластера Redis

Кластер Redis имеет фиксированные хэш-слоты `16384`. Для каждого `key` вычислите значение `CRC16`, а затем возьмите модуль `16384`, чтобы получить хеш-слот, соответствующий ключу.

Каждый мастер в кластере Redis будет занимать несколько слотов. Например, если имеется 3 мастера, каждый мастер может содержать более 5000 хэш-слотов. Хэш-слот упрощает добавление и удаление узлов. При добавлении мастера туда будет перемещена часть хеш-слота других мастеров. Если мастер удален, его хэш-слот будет перенесен на другие мастера. Стоимость перемещения хэш-слота очень низкая. API клиента может позволить указанным данным проходить через один и тот же хеш-слот, что реализуется через `hash tag`.

Если какой-либо компьютер выйдет из строя, два других узла не пострадают. Потому что ключ ищет хэш-слот, а не машину.

![hash-slot](./images/hash-slot.png)

### Высокая доступность и принцип переключения активный/резервный кластера Redis

Принцип высокой доступности кластера Redis практически аналогичен Sentinel.

#### Определить, не работает ли узел

Если узел считает, что другой узел не работает, то это `pfail`, **Субъективное время простоя**. Если несколько узлов считают, что другой узел не работает, то это `fail`, **объективное время простоя**, что практически аналогично принципу Sentinel, sdown, odown.

В пределах `cluster-node-timeout`, если узел не вернул `pong`, он считается `pfail`.

Если узел считает, что определенный узел является `pfail`, то он передаст `ping` другим узлам в сообщении `gossip ping`. Если более половины узлов думают, что это `pfail`, то он станет `fail`.

#### Фильтр из узла

Для отключенного главного узла выберите один из его подчиненных узлов, чтобы переключиться на главный узел.

Проверьте время, когда каждый подчиненный узел отключается от главного узла. Если оно превышает `cluster-node-timeout * cluster-slave-validity-factor`, то переключение на `master` **недопустимо**.

#### Выбор подчиненного узла

Каждый подчиненный узел устанавливает время выбора на основе своего собственного смещения скопированных данных ведущего. Подчиненный узел с большим смещением (чем больше копируется данных) имеет более раннее время выбора и выбирается первым.

Все главные узлы начинают голосование по выбору подчиненного устройства и голосуют за избрание подчиненного устройства. Если большинство главных узлов `（N/2 + 1）` голосуют за ведомый узел, то выборы пройдены, и этот ведомый узел можно переключить на главный.

Подчиненный узел выполняет переключение между главным и резервным узлами, а подчиненный узел переключается на главный узел.

#### Сравнить с Sentinel

Весь процесс очень похож на Sentinel, поэтому кластер Redis является мощным и напрямую интегрирует функции репликации и дозорного.
