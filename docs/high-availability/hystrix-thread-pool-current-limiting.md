# Углубленная изоляция пула потоков Hystrix и ограничение скорости интерфейса.

Мы говорили о кэше запросов Hystrix, плавном откате и быстром автоматическом выключателе. В этой лекции давайте подробно поговорим об изоляции пула потоков Hystrix и ограничении скорости интерфейса.

![hystrix-process](./images/hystrix-process.png)

Hystrix выполняет функцию ограничения скорости, определяя, заполнен ли пул потоков или семафор, и напрямую отклоняет запросы, которые превышают пропускную способность, и принимает резервный вариант.

Ограничение скорости предназначено для ограничения доступа к серверным службам. Например, вы ограничиваете доступ к MySQL, Redis, Zookeeper и другим различным внутренним ресурсам промежуточного программного обеспечения. Фактически, это делается для предотвращения прямого воздействия чрезмерного трафика на серверные службы.

## Разработка технологии изоляции пула потоков

Hystrix использует технологию изоляции Bulkhead Partition для изоляции ресурсов от внешних зависимостей, тем самым предотвращая сбой любых внешних зависимостей, приводящий к сбою службы.

Под **изоляцией переборок** подразумевается разделение внутреннего пространства корабля на несколько отсеков. Если определенные отсеки повреждены и затоплены, вода не будет течь между ними. Таким образом, корабль по-прежнему будет иметь достаточную плавучесть и устойчивость в случае повреждения, что снижает риск немедленного кораблекрушения.

![bulkhead-partition](./images/bulkhead-partition.jpg)

Hystrix использует отдельный пул потоков для каждой внешней зависимости. В этом случае, если задержка вызова для этой внешней зависимости очень серьезна, в лучшем случае она исчерпает только пул потоков самой зависимости, не затрагивая другие вызовы зависимостей.

## Сценарии, в которых Hystrix применяет механизм пула потоков

- Каждый сервис вызывает десятки серверно-зависимых сервисов, и эти серверно-зависимые сервисы часто разрабатываются множеством разных команд.
— Каждая служба, зависящая от серверной части, будет предоставлять свою собственную библиотеку клиентских вызовов. Например, если используется бережливость, будет предоставлена ​​соответствующая зависимость бережливости.
- Библиотека вызовов клиентов может быть изменена в любое время.
— Библиотека вызовов клиента может добавить новую логику сетевых запросов в любое время.
- Библиотека клиентских вызовов может содержать такую логику, как автоматическая повторная попытка, анализ данных, кэширование в памяти и т. д.
- Библиотека вызовов клиента обычно представляет собой черный ящик для вызывающего абонента, включая детали реализации, доступ к сети, конфигурацию по умолчанию и т. д.
— В реальной производственной среде часто появляются звонилки и вдруг с удивлением обнаруживают, что в библиотеке вызовов клиента произошли какие-то изменения.
— Даже если библиотека вызовов клиента не изменится, сам зависимый сервис может претерпеть логические изменения.
— Некоторые зависимые клиентские библиотеки вызова могут также извлекать другие зависимые библиотеки, и эти зависимые библиотеки могут быть настроены неправильно.
— Большинство сетевых запросов выполняются синхронно.
— Сбои и задержки вызовов также могут возникать в коде самой клиентской библиотеки вызовов, не обязательно в сетевых запросах.

Проще говоря, вы должны предположить, что библиотека вызовов клиента ненадежна и может измениться в любой момент, поэтому вы должны использовать принудительную изоляцию, чтобы гарантировать, что любой сбой службы не повлияет на текущую службу.

## Преимущества механизма пула потоков

— Любая зависимая служба может быть изолирована в собственном пуле потоков. Даже если ресурсы собственного пула потоков заполнены, это не повлияет на другие вызовы служб.
- Служба может в любой момент добавить новую зависимую службу, поскольку даже если с этой новой зависимой службой возникнет проблема, это не повлияет на вызов других служб.
- Когда вышедшая из строя зависимая служба снова становится исправной, вызов службы можно мгновенно восстановить, очистив пул потоков. Однако если пул потоков tomcat заполнен, восстановление будет очень затруднительным.
- Если возникает проблема с конфигурацией библиотеки вызовов клиента, в любое время будет сообщено о состоянии работоспособности пула потоков, например, о количестве статистических данных об успехах/сбоях/отклонениях/тайм-аутах, а затем конфигурация вызовов зависимых служб может быть оперативно изменена практически в реальном времени без простоев.
- В зависимости от асинхронной природы пула потоков уровень асинхронных вызовов может быть построен поверх синхронных вызовов.

Проще говоря, самым большим преимуществом является изоляция ресурсов, которая гарантирует, что любой сбой зависимой службы не приведет к отключению текущей службы.

## Недостатки механизма пула потоков

— Самый большой недостаток механизма пула потоков — это повышенная нагрузка на процессор. <br>
    Помимо собственного вызывающего потока Tomcat, существует также пул потоков, управляемый самой Hystrix.

— Выполнение каждой команды зависит от независимого потока, который выполняет постановку в очередь, планирование и переключение контекста.
- Представители Hystrix привели статистику дополнительных накладных расходов, вызванных многопоточными асинхронными вызовами. Сравнивая многопоточные асинхронные вызовы + синхронные вызовы, можно сделать вывод, что API Netflix ежедневно выполняет 1 миллиард вызовов через Hystrix. Каждый экземпляр службы имеет более 40 пулов потоков, а каждый пул потоков содержит около 10 потоков. ) Наконец, мы обнаружили, что дополнительные накладные расходы использования Hystrix заключаются в том, что он вносит задержку запроса около 3 мс, а максимальная задержка находится в пределах 10 мс. По сравнению с улучшением доступности и стабильности это приемлемо.

Мы можем использовать технологию семафоров Hystrix для ограничения одновременного доступа к зависимому сервису вместо ограничения трафика за счет размера пула/очереди потоков.

Технологию семафоров можно использовать для ограничения скорости и ограничения пиков, но ее нельзя использовать для тайм-аута и изоляции служб, вызывающих задержки.

Для `execution.isolation.strategy` установлено значение `SEMAPHORE`, тогда Hystrix будет использовать механизм семафора для замены механизма пула потоков для ограничения скорости доступа к зависимым службам. Если задержка базового сетевого вызова при вызове через семафор очень серьезна, то ее нельзя истечь по тайм-ауту, а можно только заблокировать. Как только количество запросов превысит лимит семафора, ограничение скорости будет включено немедленно.

## Демо ограничения скорости интерфейса

Предположим, размер пула потоков равен 8, а размер очереди ожидания — 10. Мы установили большую продолжительность таймаута — 20 с.

Внутри команды напишите код и выполните сон, например, сон 3с.

- withCoreSize: установите размер пула потоков.
- withMaxQueueSize: установите размер очереди ожидания.
- withQueueSizeRejectionThreshold: используется вместе с withMaxQueueSize для получения меньшего значения из двух параметров размера очереди ожидания.

Если задан только размер пула потоков, а два других параметра, связанных с очередью, не заданы, очередь ожидания закрывается.

```java
public class GetProductInfoCommand extends HystrixCommand<ProductInfo> {

    private Long productId;

    private static final HystrixCommandKey KEY = HystrixCommandKey.Factory.asKey("GetProductInfoCommand");

    public GetProductInfoCommand(Long productId) {
        super(Setter.withGroupKey(HystrixCommandGroupKey.Factory.asKey("ProductInfoService"))
                .andCommandKey(KEY)
                // 线程池相关配置信息
                .andThreadPoolPropertiesDefaults(HystrixThreadPoolProperties.Setter()
                        // 设置线程池大小为8
                        .withCoreSize(8)
                        // 设置等待队列大小为10
                        .withMaxQueueSize(10)
                        .withQueueSizeRejectionThreshold(12))
                .andCommandPropertiesDefaults(HystrixCommandProperties.Setter()
                        .withCircuitBreakerEnabled(true)
                        .withCircuitBreakerRequestVolumeThreshold(20)
                        .withCircuitBreakerErrorThresholdPercentage(40)
                        .withCircuitBreakerSleepWindowInMilliseconds(3000)
                        // 设置超时时间
                        .withExecutionTimeoutInMilliseconds(20000)
                        // 设置fallback最大请求并发数
                        .withFallbackIsolationSemaphoreMaxConcurrentRequests(30)));
        this.productId = productId;
    }

    @Override
    protected ProductInfo run() throws Exception {
        System.out.println("调用接口查询商品数据，productId=" + productId);

        if (productId == -1L) {
            throw new Exception();
        }

        // 请求过来，会在这里hang住3秒钟
        if (productId == -2L) {
            TimeUtils.sleep(3);
        }

        String url = "http://localhost:8081/getProductInfo?productId=" + productId;
        String response = HttpClientUtils.sendGetRequest(url);
        System.out.println(response);
        return JSONObject.parseObject(response, ProductInfo.class);
    }

    @Override
    protected ProductInfo getFallback() {
        ProductInfo productInfo = new ProductInfo();
        productInfo.setName("降级商品");
        return productInfo;
    }
}
```

Моделируем 25 запросов. Первые 8 запросов будут зависать напрямую на 3 секунды при вызове интерфейса, а следующие 10 запросов сначала попадут в очередь ожидания, чтобы дождаться выполнения предыдущих запросов. Последние 7 запросов будут отклонены напрямую, и будет вызвана логика отката.

```java
@SpringBootTest
@RunWith(SpringRunner.class)
public class RejectTest {

    @Test
    public void testReject() {
        for (int i = 0; i < 25; ++i) {
            new Thread(() -> HttpClientUtils.sendGetRequest("http://localhost:8080/getProductInfo?productId=-2")).start();
        }
        // 防止主线程提前结束执行
        TimeUtils.sleep(50);
    }
}
```
