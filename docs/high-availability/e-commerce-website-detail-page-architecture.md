# Архитектура системы страницы сведений о продукте веб-сайта электронной коммерции

## Архитектура системы страницы сведений о продукте для небольшого веб-сайта электронной коммерции

При отображении страниц небольших веб-сайтов электронной коммерции используется идея указания всех страниц. Вся информация о продукте хранится в базе данных, а статическая система страниц заполняет данные в статический шаблон, чтобы сформировать статическую страницу, и отправляет ее на сервер Nginx. Когда пользователь просматривает страницу веб-сайта, он или она берет статическую HTML-страницу и возвращает ее напрямую, без какой-либо обработки бизнес-логики.

![e-commerce-website-detail-page-architecture-1](./images/e-commerce-website-detail-page-architecture-1.png)

Ниже приведена простая демонстрация шаблона страницы.

```html
<html>
    <body>
        商品名称：#{productName}<br />
        商品价格：#{productPrice}<br />
        商品描述：#{productDesc}
    </body>
</html>
```

Преимущество этого заключается в том, что каждый раз, когда пользователь просматривает страницу, ему не нужно выполнять какую-либо логику взаимодействия с базой данных или выполнять какой-либо код. Он может просто вернуть HTML-страницу напрямую. Скорость и производительность очень высокие.

Для небольших веб-сайтов с небольшим количеством страниц это очень практично и очень просто. Вы можете использовать скорость, freemarker, тимелеаф и т. д. на Java, а затем создать систему управления контентом страниц CMS. Когда шаблон будет изменен, нажмите кнопку, или система автоматически перерисует его полностью.

**Недостаток** заключается в том, что он подходит только для некоторых небольших веб-сайтов, например, размер страниц которых варьируется от десятков до десятков тысяч. Вы сказали, что для некоторых крупных веб-сайтов электронной коммерции с сотнями миллионов страниц каждый раз, когда вы изменяете шаблон страницы, вам необходимо сделать все эти страницы статическими. Это надежно? Если каждый рендеринг занимает несколько дней, весь ваш сайт будет бесполезен.

## Архитектура системы страницы сведений о продукте на крупных сайтах электронной коммерции

В системном дизайне страницы сведений о продукте крупного веб-сайта электронной коммерции при изменении данных о продукте сообщение об изменении будет помещено в очередь сообщений MQ. **Служба кэша** При потреблении этого сообщения из очереди сообщений она определяет, что данные изменились, а затем вызывает интерфейс службы данных для получения измененных данных, а затем отправляет интегрированные данные в Redis. Данные, кэшированные локально Nginx, имеют определенный срок, например 10 минут. По истечении срока действия данных он получит последние кэшированные данные из Redis и кэширует их локально.

Когда пользователи просматривают веб-страницы, локальные данные Nginx динамически преобразуются в локальные шаблоны HTML и возвращаются пользователям.

![e-commerce-website-detail-page-architecture-2](./images/e-commerce-website-detail-page-architecture-2.png)

Хотя это не так быстро, как прямой возврат html-страницы, это также очень быстро, поскольку данные кэшируются локально. Фактически, он потребляет только производительность динамического рендеринга html-страницы. При изменении html-шаблона нет необходимости заново статиковать все страницы и отправлять запросы. Накладные расходы на сетевые запросы отсутствуют, данные могут быть напрямую отображены в последний шаблон HTML-страницы, а затем на них отправлен ответ.

В рамках этой архитектуры нам необходимо обеспечить высокую доступность системы.

Если количество посещений системы очень велико, срок действия локального кеша Nginx истек, а кеш в redis очищен алгоритмом LRU, то объем посещений будет большим, и из службы кеша будут вызываться стандартные сервисы. Однако если в это время произойдет сбой интерфейса службы продукта и вызов будет задержан, все потоки службы кэша будут исчерпаны при вызове интерфейса службы продукта. Когда каждый поток обращается к интерфейсу сервиса продукта, он зависает на долгое время, и там зависает большое количество последующих запросов. В настоящее время службе кэширования не хватает потоков для вызова интерфейсов других служб, в результате чего все большое количество страниц с подробными сведениями о продуктах не могут нормально отображаться.

На самом деле это явление, когда сбой службы интерфейса продукта приводит к исчерпанию ресурсов службы кэша.
