# Реализовать изоляцию ресурсов на основе семафорного механизма Hystrix.

Одной из основных функций Hystrix на самом деле является так называемая **изоляция ресурсов**. Самая основная проблема, которую предстоит решить, — это изолировать вызовы нескольких зависимых служб в их собственные пулы ресурсов. Избегайте вызова определенной зависимой службы, поскольку задержка или сбой вызова интерфейса зависимой службы приведет к использованию всех ресурсов потока службы при вызове интерфейса этой службы. Как только все потоковые ресурсы службы будут исчерпаны, это может привести к сбою службы или даже к дальнейшему распространению такого рода сбоев.

Hystrix реализует изоляцию ресурсов с помощью двух основных технологий:

- Пул потоков
- семафор

По умолчанию Hystrix использует режим пула потоков.

Технология пула потоков уже упоминалась ранее. В этом разделе речь пойдет о семафорном механизме для достижения изоляции ресурсов, а также о различиях и конкретных сценариях применения двух технологий.

## Механизм семафора

Изоляция ресурсов семафора действует только как переключатель. Например, если размер семафора службы A равен 10, это означает, что он позволяет только 10 потокам tomcat одновременно получать доступ к службе A, а другие запросы будут отклонены, тем самым достигается роль изоляции ресурса и защиты с ограничением скорости.

## Разница между пулом потоков и семафором

Технология изоляции пула потоков не означает управление потоками веб-контейнеров, таких как Tomcat. В более строгом смысле технология изоляции пула потоков Hystrix контролирует выполнение потоков Tomcat. После заполнения пула потоков Hystrix он гарантирует, что потоки Tomcat не будут зависать из-за задержек или сбоев в вызовах интерфейса, которые полагаются на службы. Другие потоки Tomcat не будут зависать и могут быстро вернуться для поддержки других задач.

Технология изоляции пула потоков использует собственные потоки Hystrix для выполнения вызовов; в то время как технология изоляции семафоров напрямую позволяет потокам Tomcat вызывать зависимые службы. Изоляция семафоров — это всего лишь уровень. Через него может пройти столько потоков tomcat, сколько имеется семафоров, а затем выполниться.

![hystrix-semphore-thread-pool](./images/hystrix-semphore-thread-pool.png)

**Применимые сценарии**:

- **Технология пула потоков** подходит для большинства сценариев. Например, когда мы вызываем и получаем доступ к сетевым запросам, которые полагаются на службы, нам необходимо контролировать таймаут вызова (фиксировать исключения таймаута).
- **Технология семафоров**, уместно сказать, что ваш доступ осуществляется не к внешним зависимостям, а к некоторой относительно сложной внутренней бизнес-логике, а код внутри системы фактически не включает в себя какие-либо сетевые запросы, поэтому вам нужно только сделать обычное ограничение скорости семафоров, потому что нет необходимости фиксировать такие проблемы, как тайм-аут.

## Простая демонстрация семафора

Какие сценарии больше подходят для семафоров в бизнес-контексте?

Например, вообще говоря, наша служба кэширования может помещать некоторые данные, которые очень малы и к которым часто обращаются, в своей собственной чистой памяти.

Дай мне каштан. Как правило, после получения данных о продукте нам необходимо получить данные о географическом местоположении, провинции, городе, продавце и т. д., которому принадлежит продукт. Это может быть наша собственная чистая память, например Карта. Для такого рода логики, которая напрямую обращается к локальной памяти, для простой изоляции больше подходит использование семафоров.

Преимущество состоит в том, что вам не нужно самостоятельно управлять пулом потоков, не нужно заботиться о тайм-ауте и не нужно выполнять переключение контекста потока. Если семафор изолирован, производительность будет относительно выше.

Если это локальный кеш, мы можем получить cityName через cityId.

```java
public class LocationCache {
    private static Map<Long, String> cityMap = new HashMap<>();

    static {
        cityMap.put(1L, "北京");
    }

    /**
     * 通过cityId 获取 cityName
     *
     * @param cityId 城市id
     * @return 城市名
     */
    public static String getCityName(Long cityId) {
        return cityMap.get(cityId);
    }
}
```

Напишите GetCityNameCommand с политикой, установленной на **Семафор**. Получите локальный кеш в методе run(). Наша цель — изолировать ресурсы кода, получающего локальный кеш.

```java
public class GetCityNameCommand extends HystrixCommand<String> {

    private Long cityId;

    public GetCityNameCommand(Long cityId) {
        // 设置信号量隔离策略
        super(Setter.withGroupKey(HystrixCommandGroupKey.Factory.asKey("GetCityNameGroup"))
                .andCommandPropertiesDefaults(HystrixCommandProperties.Setter()
                        .withExecutionIsolationStrategy(HystrixCommandProperties.ExecutionIsolationStrategy.SEMAPHORE)));

        this.cityId = cityId;
    }

    @Override
    protected String run() {
        // 需要进行信号量隔离的代码
        return LocationCache.getCityName(cityId);
    }
}
```

На уровне интерфейса путем создания GetCityNameCommand, передачи cityId и выполнения метода Execute() код для получения локального кэша cityName изолирует ресурс семафора.

```java
@RequestMapping("/getProductInfo")
@ResponseBody
public String getProductInfo(Long productId) {
    HystrixCommand<ProductInfo> getProductInfoCommand = new GetProductInfoCommand(productId);

    // 通过command执行，获取最新商品数据
    ProductInfo productInfo = getProductInfoCommand.execute();

    Long cityId = productInfo.getCityId();

    GetCityNameCommand getCityNameCommand = new GetCityNameCommand(cityId);
    // 获取本地内存(cityName)的代码会被信号量进行资源隔离
    String cityName = getCityNameCommand.execute();

    productInfo.setCityName(cityName);

    System.out.println(productInfo);
    return "success";
}
```
