# Детальный контроль политики изоляции Hystrix

Hystrix реализует изоляцию ресурсов с помощью двух стратегий:

- Изоляция пула потоков
- Изоляция семафора

Фактически, можно обеспечить некоторый детальный контроль над изоляцией ресурсов.

## выполнение.изоляция.стратегия

Стратегия изоляции ресурсов HystrixCommand.run() указана: `THREAD` или `SEMAPHORE`, одна на основе пула потоков, а другая — на семафоре.

```java
// to use thread isolation
HystrixCommandProperties.Setter().withExecutionIsolationStrategy(ExecutionIsolationStrategy.THREAD)

// to use semaphore isolation
HystrixCommandProperties.Setter().withExecutionIsolationStrategy(ExecutionIsolationStrategy.SEMAPHORE)
```

В механизме пула потоков каждая команда выполняется в потоке, а ограничение скорости контролируется размером пула потоков; в механизме семафора команда выполняется в вызывающем потоке (то есть в пуле потоков Tomcat), а ограничение скорости осуществляется в зависимости от емкости семафора.

Как выбрать между пулом потоков и семафором?

**Стратегия по умолчанию** — это пул потоков.

**Пул потоков** Фактически, самым большим преимуществом является то, что для запросов доступа к сети при наличии тайм-аута можно избежать блокировки вызывающего потока.

Сценарий использования семафоров обычно предназначен для сценариев чрезвычайно большого параллелизма, где каждый экземпляр службы выполняет сотни `QPS` в секунду. Если вы сейчас используете пул потоков, потоков, как правило, будет не слишком много, и он может не поддерживать такой высокий уровень параллелизма. Если вы хотите его поддерживать, он может потреблять много ресурсов потоков, поэтому используйте семафоры для защиты с ограничением скорости. Как правило, семафоры обычно используются в некоторых службах бизнес-логики, основанных на чистой памяти, и не требуют каких-либо запросов доступа к сети.

## командная клавиша и группа команд

Мы используем изоляцию пула потоков. Как разделить **зависимые службы**, **интерфейс зависимых служб**, **пул потоков**?

Каждая команда может иметь свое имя, ключ команды и свою группу — группу команд.

```java
private static final Setter cachedSetter = Setter.withGroupKey(HystrixCommandGroupKey.Factory.asKey("ExampleGroup"))
                                                 .andCommandKey(HystrixCommandKey.Factory.asKey("HelloWorld"));

public CommandHelloWorld(String name) {
    super(cachedSetter);
    this.name = name;
}
```

Командная группа – очень важное понятие. По умолчанию пул потоков определяется через группу команд, а некоторая информация мониторинга и сигналов тревоги также агрегируется через группу команд. Запросы в одной группе команд будут поступать в один и тот же пул потоков.

## пул командных потоков

ThreadPoolKey представляет собой HystrixThreadPool, используемый для унифицированного мониторинга, статистики и кэширования. ThreadPoolKey по умолчанию — это имя группы команд. Каждая команда будет привязана к ThreadPool, соответствующему ее ThreadPoolKey.

Если вы не хотите использовать группу команд напрямую, вы также можете вручную задать имя ThreadPool.

```java
private static final Setter cachedSetter = Setter.withGroupKey(HystrixCommandGroupKey.Factory.asKey("ExampleGroup"))
                                                 .andCommandKey(HystrixCommandKey.Factory.asKey("HelloWorld"))
                                                 .andThreadPoolKey(HystrixThreadPoolKey.Factory.asKey("HelloWorldPool"));

public CommandHelloWorld(String name) {
    super(cachedSetter);
    this.name = name;
}
```

## командный ключ, группа команд и пул командных потоков

**командная клавиша** представляет тип команды. Вообще говоря, он представляет собой интерфейс нижестоящего зависимого сервиса.

**командная группа** представляет определенную нижестоящую зависимую службу. Это очень разумно. Зависимая служба может предоставлять несколько интерфейсов, каждый из которых является командным ключом. Группа команд логически подсчитывает количество вызовов, успехов, таймаутов, сбоев и т. д. по набору командных клавиш, и вы можете увидеть некоторый статус доступа определенного сервиса в целом. **Как правило, рекомендуется разделить пул потоков в соответствии с зоной обслуживания. По умолчанию ключи команд принадлежат одному и тому же пулу потоков. **

Например, есть служба A. По вашей оценке, общее количество `QPS` всех интерфейсов службы A в секунду составляет около 100. У вас есть служба B для вызова службы A. Ваша служба B развернула 10 экземпляров. В каждом экземпляре используйте группу команд, соответствующую нижестоящему сервису A. Дайте пул потоков, количество составляет около 10, поэтому общий доступ QPS от сервиса B к сервису A составляет около 100 в секунду.

Однако если группа команд соответствует сервису, а интерфейсы, предоставляемые этим сервисом, имеют очень разные посещения, разница очень велика. Возможно, вы захотите включить командные клавиши, соответствующие нескольким интерфейсам, в группу команд, соответствующую этой службе, чтобы выполнить более детальную изоляцию ресурсов. **То есть мы надеемся использовать разные пулы потоков для разных интерфейсов одного и того же сервиса. **

```
command key -> command group

command key -> 自己的 thread pool key
```

Логически говоря, несколько командных клавиш относятся к одной группе команд и при ведении статистики будут учитываться вместе. Каждый командный ключ имеет собственный пул потоков, а каждый интерфейс имеет собственный пул потоков для изоляции ресурсов и ограничения скорости.

Проще говоря, если вашему командному ключу необходимо использовать собственный пул потоков, вы можете определить свой собственный ключ пула потоков, и все будет в порядке.

## размер ядра

Установите размер пула потоков, значение по умолчанию — 10. Вообще говоря, размера по умолчанию в 10 потоков достаточно.

```java
HystrixThreadPoolProperties.Setter().withCoreSize(int value);
```

## очередьSizeRejectionThreshold

Если все 10 потоков в пуле потоков работают и нет простаивающих потоков, которые могли бы делать другие дела, если в это время придет другой запрос, он сначала попадет в очередь. Если очередь невыполненной очереди заполнена и приходит еще один запрос, просто отклоните запрос напрямую, выполните резервную логику возврата и быстро вернитесь.

![hystrix-thread-pool-queue](./images/hystrix-thread-pool-queue.png)

Управляет порогом отклонения, когда очередь заполнена. Поскольку maxQueueSize не допускает горячего изменения, этот параметр можно изменить в горячем режиме, чтобы контролировать максимальный размер очереди.

```java
HystrixThreadPoolProperties.Setter().withQueueSizeRejectionThreshold(int value);
```

## выполнение.isolation.semaphore.maxConcurrentRequests

Установите максимально допустимый параллельный доступ при использовании политики изоляции SEMAPHORE. Если максимальный параллелизм превышен, запрос будет отклонен напрямую.

Настройка этого параллелизма должна быть аналогична настройке размера пула потоков, но на основе семафоров производительность будет намного лучше, а накладные расходы самого фреймворка Hystrix будут намного меньше.

Значение по умолчанию — 10. Постарайтесь установить его как можно меньшим, поскольку, если оно установлено слишком большим и возникает задержка, это может привести к мгновенному заполнению собственных ресурсов потока Tomcat.

```java
HystrixCommandProperties.Setter().withExecutionIsolationSemaphoreMaxConcurrentRequests(int value);
```
